# workshop-ui

TypeScript UI package at `crates/workshop/ui/`, a sibling of the `crates/workshop/server/` crate that builds and serves it: workshop chrome, agent controls, and the SPA served by workshop-server. `workshop-server`'s `build.rs` bundles it through `build-ui::build_sibling("../ui", ...)`.

- `src/` has three layers: `base/` (paths), `services/` (the app's services and their tokens; services own no views), and `parts/` (the feature directories - every panel extends `WorkshopPart` from `@workshop/platform/workshop-part`, hence the name). Imports flow from `parts` through `services` to `base`, never in reverse. All three layers may import `@workshop/platform`, the family's UI mechanics (lifecycle, events, the registries, the context-key and text-control services, the `WorkshopPart` base class), which never imports the app. `main.ts` is the composition root and nothing imports it. A framework contract and its service token live in `@workshop/platform` (the status bar's `STATUS_BAR`, `CONTEXT_KEY_SERVICE`, `TEXT_CONTROL_SERVICE`). Any other service token and its interface types always live in `services/`, even when the implementing widget is DOM-bound and stays in `parts/` (the closed-editor stack, the editor-settings and quick-input services): consumers import a token from `@workshop/platform` or `services/`, never from `parts/`.
- Shared state lives in a service with a change emitter, constructed once at the composition root and passed through constructors. Do not store application state in mutable module globals.
- Workshop agent controls target Cursor's workspace-sidebar agent surface, not the Glass Agents Window or editor-tab agent. Workbench chrome uses VS Code theme tokens, and Cursor-native controls use the shared Cursor design tokens.

## Commands, menus, and keybindings

The workbench follows VS Code's mechanics: a command registry, a menu registry keyed by `MenuId`, a keybinding registry with a pure chord resolver, a context-key service with a `when` expression language, and a prefix-keyed quick-access registry. All of them come from `@workshop/platform`.

- Registries live in `@workshop/platform`, and services own no views. `Commands`, `Menus`, `KeybindingsRegistry`, and `QuickAccessRegistry` are module-level singletons; contribution files write to them at module scope, before any service exists. They hold registration data, not application state - the no-mutable-globals rule above still governs state. `ContextKeyService`, `QuickInputService`, `EditorSettingsService`, `TextControlService`, and `RecentFilesStore` are services resolved with `getService`. Each service token lives in its own service module (`CONTEXT_KEY_SERVICE` in `@workshop/platform/context-key-service`, for example), created with `createServiceToken` from `@workshop/platform/service-registry`. The DOM-bound services keep their implementations in `parts/`, but their tokens and interface types live in `@workshop/platform` or `services/`: `STATUS_BAR` (`@workshop/platform/status-bar`), `CLOSED_EDITORS` (`services/closed-editors.ts`), `EDITOR_SETTINGS_SERVICE` (`services/editor-settings-service.ts`), `QUICK_INPUT_SERVICE` (`services/quick-input-service.ts`), and `COMMANDS_HISTORY` (`services/commands-history.ts`, implemented in `parts/quickinput/commands-history.ts`).
- Register work through `registerAction` (`@workshop/platform/action-registry`). One descriptor fans out into the command registry (with metadata), one menu row per `menu` entry plus a Command Palette row when `f1` is set, and the keybinding rule with `precondition` ANDed into its `when`. Every `when`/`precondition`/`toggled`/keybinding string is parsed once at registration; a malformed string comes back as a `ParseError` value, never a throw at render.
- Command ids and context-key names are VS Code's, verbatim: `workbench.action.files.save`, `workbench.view.explorer`, `editor.action.clipboardCutAction`, and context keys `editorTextFocus`, `inputFocus`, `textInputFocus`, `sideBarVisible`, `auxiliaryBarVisible`, `statusBarVisible`, `isFullscreen`, `isWeb`, `activeEditor`, `editorLangId`, `chordPending`, `config.editor.*`. Reuse an existing id or key before inventing one; Cursor-only rows with no public id use the `workbench.action.*` namespace.
- Keybindings are chord strings (`"ctrlcmd+s"`, `"ctrl+m ctrl+o"`). `ctrlcmd` resolves to Cmd on macOS and Ctrl elsewhere; rules may include `mac`/`linux` overrides. Every Ctrl-based chord binds `ctrlcmd`.
- Each feature has an eager `parts/<feature>/<feature>.contribution.ts` holding its `registerAction` calls at module scope. Those modules sit inside the entry bundle, the eagerly loaded composition: `crates/workshop/ui/src/main.ts` and the `*.contribution.ts` modules it imports. Lazy panels never import a module inside it, directly or through another import. Everything else that eager and lazy code both import, such as `@workshop/platform`, `services/`, `base/`, and shared parts modules like `parts/layout/zones.ts`, is shared code. `run` bodies lazy-import (`() => import("./editor-commands").then(...)`) anything that pulls CodeMirror, dockview, or tiptap, so the entry bundle stays free of the feature chunks; the bundle guards in `test/` enforce this. `parts/workbench.contributions.ts` is the flat list of side-effect imports of every contribution file; `parts/menu/index.ts` imports it once.
- A feature's `index.ts` keeps only `register()` - the panel registry's activation hook, installing the panel factory, chunk-bound quick-access providers, and chunk-sourced context keys. Never `export *` from a feature `index.ts`; importers point at source files directly.
- Unimplemented menu rows live in the stub table, `parts/menu/stubs.contribution.ts`: one row per stub, registered with `precondition: "false"` so it renders disabled under its final name and shortcut. A row that lands in several menus lists its placements as an array. Implementing a stub means deleting its row and adding a `registerAction` in the owning feature's contribution file - no menu, test, or keybinding changes.
- The editor tab's right-click menu is `MenuId.EditorTitleContext`; a feature adds a tab-menu row by placing it there. Every dock panel uses one generic tab, `parts/layout/panel-tab.ts`, registered as Dockview's default tab component: a closable panel type gets the close button and the tab menu, while a type registered `closable: false` gets neither. The close button and Delete on the focused tab run the layout core's close path in `parts/layout/panel-close.ts` with `{ panelId }`, so the part confirms first, and `parts/layout/layout.contribution.ts` registers Close (`workbench.action.closeActiveEditor`) and Close Others (`workbench.action.closeOtherEditors`) over the same path. The tab opens the menu at the pointer through `Menu.open(menuId, anchor, context, overlay)`: the context `{ panelId }` is the first run argument of every row, so rows act on the clicked tab rather than the active one, and the overlay `{ activeEditor: <the clicked panel's type> }` is read before the global context-key service for row `when`, `precondition` and `toggled`, for submenus, and for keybinding labels.
- The status bar hosts indicator slots (`STATUS_INDICATORS` in `@workshop/platform/status-indicators`): a feature registers `{ id, name, order, decorative? }` and drives the returned handle with `set("green" | "amber" | "red" | null, tooltip?)`, and the bar renders one LED per id in ascending `order`. The bar paints only text, tooltip and barberpole; each LED belongs to its owner, such as the activity LED in `parts/status/activity-indicator.ts` and the recording LED, which `main.ts` registers before the layout restores and hands to dictation through `STT_STATUS` (`services/stt-status.ts`). `main.ts` is the one place contributions are wired: it builds the indicators, routes the socket's status frames to them, and registers the product's tokens.
- Widgets live in `parts/`: the menubar (`parts/menu/menubar.ts` + `menu.ts`), the capture-phase keybinding dispatcher (`parts/layout/keybinding-dispatcher.ts`), quick input (`parts/quickinput/`), and the title-bar command center (`parts/chrome/command-center.ts`). One resolver owns every key; a chord claimed by any rule is swallowed even when its `when` fails.
