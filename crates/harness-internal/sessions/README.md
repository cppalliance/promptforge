# harness-sessions

The Harness session layer: agent discovery, session state, the input wait registry, and the supervisor state machine that takes a run from alive through closing to closed. Every run resolves its declared capabilities against the registry and services the Host hands `Harness::new`, plus the built-in `promptforge/web` each gateway generation builds when the Host registered none, and the crate is what `harness`'s `Session` drives. Private to the Harness family in `crates/harness-internal/`; clients reach it through the `harness` facade. Like every Harness crate, it may depend only on `promptforge` and its container siblings.

`WaitRegistry` holds a session's unresolved user-input waits behind single-use cryptographic tokens, retained across socket loss and resent on reconnect. `SessionInputBroker` is the session's `InputBroker`, handed to each run it launches as the input service the `promptforge/user-input` ask tool waits on, which registers a wait, pushes the durable `WaitFrame::Required` itself, and suspends until the session completes the wait with the operator's text byte-exact. A drop guard turns every dying wait into a durable `WaitFrame::Cancelled`, so a cancelled turn never leaks a wait or leaves a stale prompt. The frames are Harness data; the client owning the socket renders them into its own protocol.
