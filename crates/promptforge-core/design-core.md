# `promptforge-core` produces bound, isolated Markdown prompt runs

## Executive summary

`promptforge-core` is the library that turns one PromptForge Markdown source into a validated run result. A host creates one execution id, parses the source into `Prompt`, binds its semantic tool and model capability declarations into an immutable `BoundPrompt`, supplies one raw input string, a complete live tool registry, a model catalog, a run-scoped virtual file store, and an observer, then awaits `execute::run` under that same id. The language requires one H1, permits one immediately leading shared `lua` program, and executes top-level H2 sections in file order. Each section owns one isolated Lua 5.4 VM from shared load through preamble, model work, `reply` binding, and epilog, then destroys it. No Lua memory crosses sections; `StoreRef` and the previous section's `reply` text are the intentional mutable channels.

Prompts depend on semantic aliases, never deployment tool or model vendor strings. H1 `tools.need` declarations bind once through the prepared picker to stable `ToolId` values, `tools.always` explicitly selects genuinely universal aliases, and H2 `tools.add` explicitly selects section-local aliases. H1 `models.need` declarations filter a host `ModelCatalog` then resolve descriptions through the same picker stack into frozen `ModelBindings`; H2 `models.use` selects at most one binding per section, and omitting it keeps the host default client model. Binding is one-to-one, immutable, and complete before execution. The observer reports deterministic borrowed `(execution, section, detail)` strings and cannot steer behavior. Fixed runtime details are payload-free, including `Model turn truncated` after a successful non-empty final-text parse. Empty model product is always `Error::EmptyModelReply` (observed as `Model turn failed`), never a soft empty success; response wire quirks concentrate in `CompletionNormalizer`. Constrained phase-local Lua `log(message)` calls supply the sole author-controlled `Lua: <message>` exception. Opt-in `DebugCapture` on `RunOptions` receives owned raw request and response JSON without widening the observer. Expected parse, binding, Lua, substitution, model, tool, and store failures return errors. The authoritative result is one string, selected by scalar Lua return, frontmatter fallback, last model reply, or `"done"`.

## Key design choices

1. **A run is a free function over caller-owned resources.** The public path is parse, bind, then `execute::run`; there is no executor object or process-global run state. The caller owns the execution id, prompt, live tools, model catalog, store, observer, optional gateway client, and optional `DebugCapture`, which keeps deployment policy outside the core and makes concurrent runs independent.

2. **One required H1 is the semantic prompt boundary.** Frontmatter is followed by exactly one non-empty H1, with ordinary Markdown before it ignored. The H1 supplies the stable run title and the only location for shared declarations, so parsing refuses a missing or duplicate H1 instead of inferring intent from an H2 or preserving an unreleased grammar.

3. **One exact leading `lua` fence carries shared code.** Blank lines may separate H1 from the exact unindented fence; only the leading position is reserved, so a `lua` fence after description prose remains prose exactly as it does inside a section. A single reserved position makes executable shared code visually and mechanically unambiguous while leaving near-miss and nested Markdown markers as prose. The removed `lua prompt` info-token form is a parse error in the leading position, naming the removed form, because such a fence is almost certainly a stale prompt from before the change.

4. **Every section has preamble, prose, and epilog phases.** An exact leading `lua` fence is the optional preamble, an exact trailing `lua` fence is the optional epilog, and the middle remains model-facing prose. Positional reservation preserves ordinary fenced examples and gives authors one predictable place for setup and one for processing the final reply.

5. **Lua compiles at parse time and bytecode stays process-local.** `LuaProgram` retains source for diagnostics and private Lua 5.4 bytecode for repeated loading. A successful `Prompt` is syntactically executable, while bytecode is never persisted or treated as portable because coupling stored prompts to one Lua build would create a fragile compatibility format.

6. **One isolated VM survives the whole section lifecycle.** Shared code, host injection, preamble, model await, `reply` binding, and epilog use one `SectionVm`; the VM is destroyed before fall-through. This preserves section-local helpers and variables across the await without permitting accidental cross-section Lua state.

7. **Scalar Lua return is the only early exit.** A top-level string, integer, number, or boolean return becomes the run result; nil continues and unsupported values fail. A preamble return skips model and epilog, while an epilog return follows the model turn. One exit mechanism keeps control flow compact and avoids generated control tools or a second result channel.

8. **The store and reply are the intentional mutable state across sections.** One caller-owned `StoreRef` handle exposes a run-scoped virtual filesystem with write, append, read_lines (numbered), read (verbatim), inject (verbatim + untrusted envelope), string replacement, delete, and glob operations. The previous section's model reply text also carries forward as the Lua global `reply` (nil in section 1) and as `{{ reply }}` in prose substitution. Section VMs and conversations are discarded, so durable cross-section state is explicit and future parallel execution is not constrained by hidden Lua memory.

9. **Prompts declare semantic needs under local aliases.** H1 uses `tools.need(alias, description)` and `models.need(alias, description, opts?)` with a case-sensitive alias matching `[A-Za-z][A-Za-z0-9_-]{0,63}` and an author-register capability sentence. Optional model `opts` is a Lua table: `context` and `thinking` filter the catalog; `temperature`, `max_tokens`, and a requested `thinking` switch freeze onto the binding's invocation. Hosts own concrete availability, so a prompt can move between deployments without changing provider names, server names, or transport wire names.

10. **Tool exposure and model selection are always intentional.** Declaring a need exposes nothing and selects no model. H2 `tools.add(alias)` is the normal tool scope, while H1 `tools.always(alias)` is reserved for capabilities needed in every model-facing section. H2 `models.use(alias)` selects at most one frozen binding before scope close; absence means the host default client model. No automatic injection exists because least scope is easier to audit and prevents unrelated tools from competing in a model turn.

11. **Binding freezes one-to-one alias and identity maps for tools and models.** `bind_prompt` resolves H1 tool declarations synchronously through one prepared `ToolPicker`, validates the complete live `ToolRegistry`, and atomically creates forward and reverse maps. Model declarations filter the host `ModelCatalog` by hard constraints, rebuild a picker over the survivors (reusing the tool picker's embedder), and freeze `ModelBindings`. The model picker catalog encodes each `ModelId` out of the picker's embedding name (a neutral `model` label) so vendor ids like `claude-sonnet-4-6` cannot drown the capability description. Duplicate live tool IDs, duplicate aliases, two tool aliases selecting one ID, and selected IDs absent from the registry all fail before execution. Model aliases that share catalog weights under different invocation params are legal and are not rejected as identity collisions. Prompts with no `models.need` accept an empty catalog; a declared need against an empty catalog is `ModelAbsent`.

12. **Effective-scope overlap fails before a model sees tools.** Binding reuses picker vectors to precompute selected near-duplicate pairs, and execution checks only the `always` plus `add` aliases competing in the current non-empty turn. Similar tools may exist in different sections, but a pair at or above the configured duplicate threshold fails with both identities and the measured score because asking the model to distinguish semantically duplicate choices is less reliable than fixing the prompt scope.

13. **The observer reports facts through one non-blocking seam; raw payloads use a separate opt-in.** Every observed API takes an always-present `&dyn Observer`; silence is `NullObserver`. The caller supplies one execution id before parsing and passes it unchanged through binding and `RunOptions`; `SectionVm` retains it for synchronous Lua and store reports, and model and tool loops borrow it from run state. Parse, compilation, binding, registry validation, Lua phases, scope, model, tool, run, section, and harness-mediated store boundaries emit deterministic payload-free section and detail strings under that id. After a successful model turn that binds non-empty final text, a choice whose `finish_reason` is `length` also reports `Model turn truncated` (alongside `Model turn completed`). A turn with neither non-empty tool calls nor non-empty text fails as `EmptyModelReply` before reply binding and is observed as `Model turn failed`; the retained `Model reply was empty` constant is not emitted on that path. During H1 binding, H1 replay, H2 preamble, H2 epilog, and compatibility chunk execution, a phase-local `log(message)` callback may add the sole dynamic detail form, exactly `Lua: <message>`. It validates one UTF-8 string, at most 256 characters and free of newline and control characters, and its borrowed observer expires before the phase returns. Observer implementations own synchronization, so a shared recorder uses its own mutex and core never holds a global observer lock or a recorder guard across an await. Reports never feed back into execution, so observer choice cannot change output, errors, order, or side effects. Hosts that need request or response bodies set `RunOptions::debug` to a `DebugCapture`; production leaves it `None` and pays nothing. Capture events are owned `serde_json::Value` bodies plus optional `finish_reason` and `reasoning_content`, never routed through `Observer`.

14. **Untrusted and executable content stay visibly separated.** Lua runs in a restricted VM with direct `print`, code-loading, and reflection surfaces removed and one section-wide instruction budget. The constrained observer-backed `log(message)` callback is the only output surface. Tool results marked untrusted are nonce-framed before entering model history. These boundaries make prompt code explicit and fetched text data, while expected hostile or malformed input returns an error instead of widening authority.

15. **Reranking and generated progress labels remain outside core.** The picker spike measured `bge-reranker-v2-m3` at 0.856 on the clean hackathon set but 0.735 on TOOLRET, below plain bge-small at 0.804, while adding a roughly 568M-parameter model. That domain-dependent result does not justify a mandatory reranker; author-register measurements on a deployment's own catalog must first show reliable benefit. The original `(execution, section, detail)` record remains the authoritative trace. A future label model may derive optional UI text off the critical path, but it may neither replace that record nor influence execution, and it must independently justify quality, latency, and privacy cost.

16. **Complete prompt fixtures live at the public crate boundary.** The unpublished `promptforge-core-tests` workspace binary owns readable, author-shaped valid, invalid, and deterministic execution Markdown documents. Each fixture is named and registered explicitly with `include_str!`; table-driven offline unit tests assert complete parsed structure, public error variants plus stable message fragments, exact author checkpoint order, scalar preamble early return, and cross-section store fall-through. Tool-free execution fixtures run shared declarations through public `bind_tool_declarations` with a deterministic no-tools resolver, then use the public parsed-`Prompt` temporary path rather than constructing a semantic picker. One mutex-backed observer records stable execution IDs, and a concurrent regression partitions one shared trace by ID to prove runs cannot be confused. A separate repository-prompt smoke test intentionally discovers every shipped Markdown prompt, rejects concrete tool names, and requires each to parse. Complete-registry semantic binding remains in the MCP server owner test, where the real picker and live registry are already provisioned. Narrow fence near-misses, malformed fields, instruction budgets, mock wire behavior, and other isolated mechanics remain inline with their owning crates. This keeps whole-document stories visible without adding generated loaders, model loading, production-tool provisioning, external processes, live network requests, gateway calls, generation-model calls, or a second parser contract.

17. **Real-model behavior is explicit, pinned, and direct.** The same unpublished test crate provisions per-kind pinned artifacts with every URL and SHA-256 committed: the scenario kind pairs official CPU-only llama.cpp release b10082 archives with the official Qwen3-0.6B Q8 GGUF, and the dev kind pairs GPU-enabled archives from that same release (Vulkan, with Metal reused on macOS and a CPU fallback on Windows arm64) with the community unsloth Qwen3.5-9B Q4_K_M GGUF, installed under distinct platform keys so both coexist in one cache and one kind never downloads the other's assets. The explicit binary is the only live-model entry point - `cargo run -p promptforge-core-tests` runs the fixed scenarios and its `dev` subcommand runs any prompt file - while ordinary tests retain loopback fake servers, temporary caches, tiny archives, and test-executable copies and never contact an official host or launch llama-server. Both paths start the pinned server directly and point `GatewayClient` at its loopback OpenAI `/v1` endpoint, so no promptforge-gateway process or credential participates. A process guard makes at most four fresh-port attempts, assigns each child a unique model alias and bearer token, and checks child liveness around successful health and authenticated model-list probes before accepting readiness. A child that exits while another listener remains on its selected port is retried as a bind collision; other early exits fail immediately. Each attempt has a 180-second deadline, stdout and stderr drain continuously into independent 64 KiB tail buffers, diagnostics redact the bearer token, and dropping the guard kills and waits for the child on success, returned error, panic unwinding, or Ctrl-C, including cancellation during blocking model startup. The exact scenario server policy is one slot, seed 424242, temperature zero, 4096 context tokens, 256 generated tokens, Jinja enabled, reasoning disabled, and `deepseek` reasoning parsing to remove Qwen's empty thinking envelope. One fixture requires nonempty marked text and proves epilog visibility in one turn. The other exposes one concrete required-string schema under a distinct local alias, rejects malformed arguments in the tool itself, returns a deterministic tool result, and proves one aliased dispatch, continuation to a nonempty marked final answer, epilog visibility, and exactly two turns under its declared two-turn cap. These are behavioral assertions rather than exact prose snapshots. The dev profile instead serves interactive prompt development: a 131072-token default context, an 8192-token generation ceiling, full GPU offload, a q8_0 KV cache, and thinking enabled with model-card sampling, tunable through `--context`, `--max-tokens`, and `--no-think`. The dev runner mirrors the CLI pipeline - read, require the `promptforge:` version, parse, build the live registry (`web_fetch` always, gateway-backed `web_search` only when `PROMPTFORGE_TOKEN` is present), bind, and execute - under a per-run `dev-` execution id, streaming every observer record to stderr while stdout carries only the result, and `--watch` reruns the file after each debounced save against the warm guarded server. All of it is verified against the real models, including cache-only reruns, the loud `Absent` failure for an unavailable capability, and Ctrl-C teardown leaving no orphan server.

18. **Completion normalization is the response-side wire seam.** `GatewayClient::complete` runs an `Arc<dyn CompletionNormalizer>` (default `OpenAiChatNormalizer` in `normalize.rs`) over the OpenAI-shaped JSON body before the tool loop consumes a turn. A normalized turn must yield non-empty tool calls or non-empty text; anything else is `Error::EmptyModelReply`, including when reasoning side-channel text is present. Reasoning fields (`reasoning_content`, `reasoning`, `thinking`) never become answer text; they ride on `DebugCapture` only. Tool-call turns with empty `content` remain valid product. Growth of this module is expected: concentrate dialect cases here rather than scattering them through execute or hosts.

## The public lifecycle separates syntax, deployment binding, and execution

`Prompt::parse(source, execution, observer)` validates Markdown structure, compiles executable Lua regions, reports under the caller's execution id, and returns a `Prompt`. Its frontmatter carries `name`, `description`, optional `promptforge` engine major, optional `default_return`, and optional `max_tool_iterations`. It carries no tool list. The parsed value contains the required title, optional shared program, H1 description text, and top-level section tree.

`bind::bind_prompt(prompt, picker, registry, models, execution, observer)` consumes a parsed prompt and returns `BoundPrompt`. The pass executes shared Lua once in declaration mode, resolves exact tool capability-description bytes at most once during that pass, filters and resolves `models.need` against the host `ModelCatalog`, retains selected descriptors for diagnostics, validates both tool identity directions, and asks the tool picker for near-duplicate analysis without embedding new text. `Absent`, `Duplicate`, and `Ambiguous` are distinct binding outcomes for tools and for models. Binding performs no chat completion or tool call and reports under the same id parsing used. Shared-code `log(message)` calls report under the H1 title during binding and under the current H2 title during exact replay.

`execute::run(bound, args, tools, store, RunOptions)` gates the `promptforge` major, walks top-level H2 sections in source order, and returns one string. Parsed `Prompt` input remains accepted as a temporary path for tool-free callers, but it runs on the same validated execution path as a bound prompt with empty frozen bindings: there is exactly one `tools.add`, every section closes its tool and model scope, and a `tools.need`, `tools.add`, `models.need`, or `models.use` in an unbound prompt fails loudly instead of being recorded. Semantic declarations require `BoundPrompt`. After H2 scope close, a selected `models.use` binding supplies per-call `CompletionOptions` (`model`, `temperature`, `max_tokens`, optional `chat_template_kwargs.enable_thinking`) for every complete in that section; otherwise the host client's construction-time model is used with no extra sampling fields. `RunOptions` always carries the caller's execution id and observer, optionally carries a configured gateway client, and optionally carries a `DebugCapture`. That client is a transport seam rather than a mandatory promptforge-gateway hop, which lets the explicit test harness connect it directly to pinned llama-server while production hosts retain gateway routing. The async future remains sendable, and no store, recorder, or observer mutex guard crosses a model await.

## Exact grammar keeps Markdown examples inert

Every reserved opening line is exactly ```` ```lua ```` and every closing line is exactly ```` ``` ````, for the H1 shared library and section executable fences alike. Openers are unindented and lowercase, with no extra info tokens. Longer markers, indentation, other capitalization, other languages, extra info tokens (including the removed `lua prompt` form), and marker-looking lines nested inside a longer fence remain prose, except that an H1 opening with the removed `lua prompt` form is a parse error naming it.

An H2 section may contain one leading executable fence and one trailing executable fence. One boundary fence is the preamble. Two may surround empty prose. An exact Lua fence in the middle of prose remains prose. An unclosed reserved boundary is an error located at the prompt region and phase. H3 through H6 children are parsed into the section tree but are not independently executed by the current fall-through runtime.

Substitution applies only to prose. `{{ args }}` reads the single raw input string, `{{ reply }}` reads the previous section's model reply text (nil in section 1; using it when nil is a hard error), `{{ var.x }}` reads section-local Lua values, and `{{ sys.when }}`, `{{ sys.now }}`, and `{{ sys.id }}` read runtime metadata. Scalars render as strings, tables render as JSON, and a missing path is an error. Lua `sys` is sealed: unknown field reads and any writes raise. Lua source is never substituted.

## Section execution preserves local context and explicit fall-through

For each top-level section, execution creates a fresh `SectionVm`, loads shared bytecode, injects `args`, `sys`, a new `var`, the shared `store`, replay-backed `tools`, and the previous section's `reply` (nil in section 1), then runs the preamble. Shared functions can read host globals after injection because they retain the same environment. H1 declaration calls replay exactly from immutable bindings and perform no embeddings. Binding, replay, preamble, and epilog each install a fresh borrowed `log` callback only for the duration of that Lua call; captured references expire at the phase boundary, and no callback or observer reference exists during a model await.

If the preamble returns nil, execution closes tool and model scope and substitutes prose. Empty prose skips overlap validation and the model, leaves `reply` nil, and still runs the epilog. Non-empty prose validates the effective tool scope, advertises each live description and parameter schema under its local alias, and enters the model tool loop under the section's selected model binding or the host default. Returned aliases dispatch through frozen `ToolId` values into the complete live registry. Final non-empty model text is bound to `reply` before the epilog runs; `finish_reason == "length"` then emits its payload-free observer detail. Empty product never reaches reply binding: the normalizer returns `EmptyModelReply` and the turn fails as `Model turn failed`. When `RunOptions::debug` is set, each turn also delivers request and response capture events with owned JSON bodies.

The model loop ends on final text and is capped by `max_tool_iterations`, defaulting to 24. Falling off the last section returns `default_return` when set, otherwise the last model reply, otherwise `"done"`. Child execution, branching, retries, task descriptors, and fan-out are not inferred from headings or model text.

## Observation is authoritative trace data, not presentation text

The complete observer interface is:

```rust
pub trait Observer: Send + Sync {
    fn observe(&self, execution: &str, section: &str, detail: &str);
}
```

Before the H1 is known, parser reports use `Prompt`; prompt-wide reports use the H1 title; section reports use the H2 heading. Fixed details come from the `observe::detail` vocabulary. They contain no raw prompt prose, input, model request or reply, tool arguments or results, store path or content, credential, fetched text, capability sentence, alias, or picker candidate. After a successful non-empty final-text bind, `Model turn truncated` is a fixed detail when `finish_reason` is `length`. `Model reply was empty` remains in the vocabulary for host compatibility but is not emitted when empty product hard-fails as `EmptyModelReply` / `Model turn failed`. The sole payload-bearing detail is a validated author checkpoint with exact prefix `Lua: `. Authors must use static checkpoint labels and must never log arguments, replies, tool arguments or results, credentials, paths, store contents, or other sensitive data.

Raw model turn payloads are not observer details. The opt-in seam is:

```rust
pub trait DebugCapture: Send + Sync {
    fn on_event(&self, execution: &str, section: &str, turn_index: u32, event: DebugEvent);
}
```

`DebugEvent` carries owned request or response JSON (`finish_reason` and `reasoning_content` when the backend supplied them). Dropping every capture event cannot change the result. Production hosts leave `RunOptions::debug` as `None`; the core-tests dev runner writes `turn-N-request.json` and `turn-N-response.json` under `<prompt-stem>.store/.trace/`.

The CLI creates one execution id before parsing, fetches `GET /v1/models` when a gateway token is present, and binds against that catalog. The MCP host reuses its existing run id, soft-fails an unreachable catalog to empty (prompts without `models.need` keep working), reparses the validated catalog source snapshot under that id, and passes it through binding and execution. MCP may recognize exact details for cosmetic progress and turn counting, tolerate unknown details, and log them together with the execution id. That recognition is downstream presentation logic. No model rewrites trace records, and a generated label cannot become evidence about what executed.

## Host registries keep abstract selection and concrete dispatch in agreement

Every `Tool` exposes stable `ToolId`, transport wire name, model-facing description, parameter schema, trust classification, and async call behavior. `ToolRegistry` is a faithful ordered view of supplied live instances; binding, rather than construction, rejects repeated stable identities. The stable ID is structural and independent of the prompt alias and current transport name.

A host constructs all tools available for a run and derives the picker catalog from those same instances. It also builds a `ModelCatalog` from gateway `GET /v1/models` (or a pinned offline entry such as the dev runner's Qwen catalog). The CLI binds synchronously and hard-fails catalog fetch when a token is present. The MCP server prepares one picker, registry, and model catalog at boot (soft-failing fetch to empty), binds on Tokio's blocking pool, and then executes asynchronously with the same observer. This construction rule prevents the picker from selecting a tool identity that has no callable implementation, and prevents `models.need` from binding an identity the host did not advertise.

## Completion normalization concentrates response wire quirks

`GatewayClient` holds `Arc<dyn CompletionNormalizer>`, defaulting to `OpenAiChatNormalizer`. `complete` normalizes the response body into a `NormalizedTurn` (`outcome`, `finish_reason`, optional `reasoning_content`) before execute sees it. The empty-response invariant is enforced here: non-empty `tool_calls` yield `ToolCalls`; else non-empty `content` yields `Text`; else the result is `Error::EmptyModelReply`. Reasoning is never promoted into the answer, even when it is the only non-empty string on the wire. Soft success with `Text("")` is forbidden. Request-side thinking dialects remain in `CompletionOptions` for now; if a matching request normalizer appears later, it belongs in the same module family. Accreting dialect cases in `normalize.rs` is the intended design pressure valve.

## Explicit fanout maps a worker section over a static item list

A parent H2 section's preamble or epilog may call `fanout("### Worker", "### List")` to run the worker template once per item parsed from the list sibling. Headings must include the `###` markers and match sibling names exactly; bare names are a hard error listing available siblings. The list section is a list-only H3 (no preamble, no epilog) whose prose contains only bullet items parsed at load time. Unordered (`- `, `* `) and ordered (`N. `, `N) `) markers are stripped; blank lines are ignored; non-list content in a list section is a parse error; an empty items list is a parse error.

Arms execute sequentially in v1. Each arm gets a fresh `SectionVm` with `item` (the list text) and `sys.taskid` ("1", "2", ...) injected before the preamble runs. `item` is available as a Lua global in preamble and epilog, and as `{{ item }}` in prose substitution. `{{ item }}` outside a fanout arm is a hard error. Arms share the run's `StoreRef`, so store writes from arm epilogs are visible to the invoker's reduce. `fanout` returns an ordered Lua table of arm reply strings. Fail-fast: the first arm error aborts the fanout and propagates to the invoker.

Children never execute by fall-through. Only an explicit `fanout(...)` call from the parent's preamble or epilog triggers child execution. Inferred fanout from heading structure remains a non-goal.

## Failures are values and non-goals remain explicit

Malformed frontmatter or Markdown, unsupported engine version, Lua compilation or execution failure, invalid Lua log arguments, replay mismatch, invalid alias, tool or model binding abstention or ambiguity, identity collision, missing scoped alias, missing live target, near-duplicate effective tool scope, substitution failure, model transport failure, empty model product (`EmptyModelReply`), tool failure, tool-loop exhaustion, and store failure are returned through the crate's error surface. A source refused by the engine-version gate emits no run reports; a started run emits a final success or failure report.

Persistent bytecode, compatibility parsing for the removed grammar, cross-section Lua memory, child execution by fall-through, branching, retries, parallel or nested fanout, dynamic fanout (Lua table as item source), reranking, and model-generated authoritative progress labels are non-goals. The separate `run_chunk` API remains only as one-phase Lua compatibility for library callers, and parsed-prompt execution remains temporarily for tool-free callers; both run the same validating `tools` table with empty frozen bindings, and neither changes the prompt grammar or semantic binding contract.
