# Gateway TTS Endpoint: `POST /v1/audio/speech` with Orpheus 3B

**Report type:** Analytical / recommendation (implementation specification)

## Executive summary

Add text-to-speech to the gateway as a fourth routed model kind: a `ModelKind::Speech` variant, an OpenAI-shaped `POST /v1/audio/speech` route, and a `send_speech` method on the `Upstream` trait that streams binary audio back to the caller. This mirrors the existing embedding and classifier routes exactly, and it is the pattern that fits TTS, because TTS is dual-use (prompt pipelines call it as a model; the Workshop plays assistant replies) and cloud passthrough (Together AI, OpenAI, any OpenAI-shaped provider) is a legitimate backend. The engine-slot pattern used for STT (`[[stt_model]]` + `gateway-stt` + in-process whisper) was rejected for TTS because STT's defining constraint - audio never leaves the machine - does not apply to synthesis, and the STT pattern has no remote-passthrough story.

The target local engine is Orpheus TTS 3B (Llama-3B backbone + SNAC neural codec), chosen for human-grade conversational prosody after sub-100M phoneme models (Kokoro, Piper) were evaluated and rejected on quality. On the 24 GB VRAM cards this project targets, Orpheus 3B at Q8 (~8 GB runtime: weights plus SNAC decoder plus KV cache) co-resides with the whisper STT pair (~3 GB) and a 14B-class authoring LLM (~10-12 GB) inside the existing dominion budget machinery - with essentially no headroom left over.

The local half of the feature no longer rests on unproven machinery: native Orpheus serving exists off the shelf. CrispASR (MIT, C++/ggml) ships prebuilt Windows x86-64 CUDA binaries with an OpenAI-compatible `/v1/audio/speech` and streaming PCM, and candle carries a merged, first-party SNAC decoder plus a complete Orpheus example (Apache/MIT). The recommendation is therefore phased: ship the route, kind, wire types, and remote passthrough first (Together AI serves `canopylabs/orpheus-3b-0.1-ft` in an OpenAI-compatible speech dialect), then land local Orpheus behind the same route after a timeboxed spike chooses between a managed CrispASR child and a hybrid that serves the Orpheus GGUF through the existing llama-server machinery and decodes SNAC in-process. Confidence: high on the routing design, medium-high on the local-engine schedule now that two working native paths exist.

## Background: the decisions already made

Three decisions from the design discussion are inputs to this report, not questions it reopens:

1. **Engine quality bar is Orpheus 3B.** Sub-100M parameter TTS (Kokoro-82M, Piper) was heard and rejected on acoustic quality: flat cadence, no semantic phrasing, no emotional range. Orpheus 3B is a speech-LLM on a Llama-3B backbone trained on 100k+ hours of English speech, with guided emotion tags and eight shipped voices (`tara`, `leah`, `jess`, `leo`, `dan`, `mia`, `zac`, `zoe`). One scoping correction: Orpheus's zero-shot voice cloning works only on the *pretrained* base model; the `orpheus-3b-0.1-ft` finetune this project targets is voice-conditioned purely by its `{name}: {text}` prompt prefix and does not clone ([prompt formatting reference](https://deepwiki.com/canopyai/Orpheus-TTS/4.2-prompt-formatting)). Cloned voices are out of scope for both phases. Sources: [GitHub](https://github.com/canopyai/Orpheus-TTS), [Hugging Face model card](https://huggingface.co/canopylabs/orpheus-3b-0.1-ft), [Together AI listing](https://www.together.ai/models/orpheus-tts).
2. **Hardware target is 24 GB VRAM cards.** The static VRAM budget: whisper STT pair ~3 GB, Orpheus 3B Q8 ~8 GB runtime (weights ~4 GB on disk, but the observed footprint including the SNAC decoder and an 8192-token KV cache is ~8 GB per practitioner measurements - [setup guide](https://localaimaster.com/blog/orpheus-tts-setup-guide), single-source impression, treat as approximate), a 14B-class Q4 authoring LLM ~10-12 GB, KV cache and OS overhead ~3 GB. The total fits a 24 GB card with essentially no headroom, so model eviction and swapping are non-goals and the dominion budget check is load-bearing, not ceremonial.
3. **TTS lives in the gateway, generalized as "audio outputters," not in-process in the Workshop.** The Workshop's voice capture moved into the gateway for the same reasons: one process owns the GPU budget, credentials, and model lifecycle, and every client (Workshop UI, CLI pipelines, MCP harness) reaches the capability through one authenticated surface.

A fourth input is architectural fact, verified in the codebase: the gateway already hosts STT in-process (`POST /v1/audio/transcriptions`, registered at `crates/gateway/src/lib.rs:303`), so the gateway is already an audio boundary in both directions conceptually; this feature completes the pair.

## The codebase offers two patterns, and TTS should take the routed one

Everything the implementor needs already exists as a working template. The two patterns:

**Pattern A - routed model kind (chat, embedding, classifier).** A model is a catalog entry with a `kind`; a route per kind guards on it; an `Upstream` trait method forwards to the backend; local models spawn as managed `llama-server` children whose serve mode derives from the kind. Touch points, all verified:

- `ModelKind` enum with serde-lowercase variants: `crates/gateway-config/src/config.rs:527-546`.
- Kind guard per route: `crates/gateway/src/routing.rs:171-181` (`require_kind`), returning the `KindMismatch` error envelope.
- Route handler template (auth, validate, `begin_inference`, model resolution, kind guard, dominion queue admit, upstream call, response validation): the embeddings handler at `crates/gateway/src/lib.rs:613-646`.
- `Upstream` trait with per-kind methods defaulting to `ModelUnavailable`: `crates/gateway-protocol/src/upstream.rs:44-148`.
- Raw POST helper that returns the upstream `reqwest::Response` untouched (the seam a binary audio stream needs): `crates/gateway-protocol/src/upstream.rs:200-229`.
- Local-child serve mode derived from kind (`--embeddings`, `--reranking`): `crates/gateway-local/src/runtime.rs:550-551` and `crates/gateway-local/src/server/support.rs:326-327`.
- Chat-only field rejection for non-chat kinds: `validate_kind_scope` at `crates/gateway-config/src/config/validate.rs:707-745`; the chat-template resolver shows the same guard at `crates/gateway-local/src/launch_templates.rs:196`.

**Pattern B - engine-slot catalog (STT).** A separate `[[stt_model]]` catalog with role slots (`interim`/`final`), a dedicated crate trio (`gateway-stt` HTTP/runtime, `gateway-transcribe` engine on worker threads, `gateway-whisper-ffi` runtime-loaded shared library), profile membership gating, and a WebSocket streaming surface (`/stt`) on the workshop listener. Touch points, all verified:

- `SttModelConfig` (`name`, `role`, `source`, `sha256`, `vram_gb`, `dominion`): `crates/gateway-config/src/config/stt.rs:38-54`.
- Profile validation of role slots (at most one interim and one final; final-without-interim is an error naming the fix): `crates/gateway-config/src/config/validate.rs:520-560`.
- Runtime provisioning through the pinned, digest-verified artifact store: `crates/gateway-stt/src/runtime.rs:123-160`; whisper library provisioning at `crates/gateway-local/src/artifacts.rs:243-256`.
- OpenAI multipart handler: `crates/gateway-stt/src/api.rs:100-118`; the `/stt` socket and capability probe: `crates/gateway-stt/src/stt.rs:36-53`; workshop-listener mounting: `crates/gateway/src/workshop.rs:105`.
- Digest-pinned recommended model pair for the Config UI: `crates/gateway-config/src/config/stt.rs:263-277`.

**Why Pattern A wins for TTS.** TTS requests are routable model calls: a prompt pipeline names a speech model the same way it names a chat model, and remote providers (Together AI lists `canopylabs/orpheus-3b-0.1-ft` at $15 per 1M characters; OpenAI ships `tts-1`/`gpt-4o-mini-tts`; ElevenLabs has its own shape) are first-class backends that Pattern B cannot express - `[[stt_model]]` has no endpoint, credential, or upstream-name concept because STT deliberately never leaves the machine. Pattern A also puts speech models in `GET /v1/models`, where clients discover them; STT models are invisible there today because they live outside the routing table, an acceptable gap for a single engine-slot pair but wrong for a capability that prompt pipelines bind by name and voice. And Pattern A reuses the dominion queue, fair scheduling via `X-PromptForge-Client`, profile allowlists, and catalog capability surfacing with no new machinery. Pattern B's genuine contribution to copy is narrower: artifact provisioning discipline and the in-process engine shape, both needed only in the local phase.

**Options considered and set aside.** Pattern B for TTS (engine-slot `[[tts_model]]`): rejected, no remote passthrough and no per-model routing. Do nothing (clients call Together AI directly): rejected, it breaks credential isolation - the gateway's founding invariant is that nothing above it holds a vendor key (`crates/gateway/README.md:7`). A generic byte-passthrough route with no `ModelKind`: rejected, it skips the kind guard, catalog metadata, and queue admission that every other workload gets.

## Specification

### 1. Config: one new `ModelKind` variant, speech-scoped validation

Add `Speech` to `ModelKind` (`crates/gateway-config/src/config.rs:527-546`): serde spelling `"speech"`, `Display` spelling `"speech"`. Most `match` sites are exhaustive and the compiler will find them - the config validator, the gateway's `require_kind` callers, the catalog serializer (`crates/gateway-config/src/config/tests/serialize.rs`). One site will stay silent and is the single most dangerous line in this feature: `launch_options` in `crates/gateway-local/src/runtime.rs:549-553` maps serve mode with a `_ => Chat` catch-all, so a `kind = "speech"` local model would compile clean and then launch as a chat `llama-server`. Add an explicit `ModelKind::Speech` arm there that returns a "local speech models are not yet supported" error until phase 2 lands `ServeMode::Speech`; never let the wildcard absorb it.

Speech models reject chat-only fields exactly as embedding and classifier models do today: `thinking`, `tool_dialect`, `default_max_tokens`, the effort knobs in `Capabilities`, and both companions (`[local_model.speculative]`, `[local_model.multimodal_projector]`). The enforcement point is `validate_kind_scope` at `crates/gateway-config/src/config/validate.rs:707-745`, called for remote models at lines 313-323 and local models at lines 397-414; extend its chat-only list so a chat-only field on a speech model is a load-time error naming the field.

Add one speech-specific capability to `Capabilities` (`crates/gateway-config/src/config.rs:557` onward): `voices: Vec<String>`, defaulting empty, surfaced verbatim on `GET /v1/models` like every other capability. Orpheus's eight named voices are catalog data the Workshop UI needs before it can offer a voice picker; an empty list means the upstream chooses. Note that voice sets are per-checkpoint: the eight English voices belong to `orpheus-3b-0.1-ft`, while the `finetune-prod` multilingual variants ship different and larger sets (one community server exposes 24), so `voices` must stay per-model data, never a shared constant. Keep `context` required for uniformity with the other kinds (validators at `validate.rs` already reject `context = 0` for every model); document it as the maximum input text tokens for speech models.

### 2. Wire protocol: JSON request in, binary audio stream out

The route speaks the OpenAI speech dialect. Request body (new `SpeechRequest` in `crates/gateway-protocol/src/wire.rs`, beside `EmbeddingRequest` at line 246): `model` (required), `input` (required, non-empty, capped - 4096 characters matches both [OpenAI's limit](https://github.com/openai/openai-python/blob/main/src/openai/resources/audio/speech.py) and CrispASR's server default), `voice` (required string; validation against the catalog's `voices` list happens at the route, not in the wire type), `response_format` (optional enum: `mp3` default, `opus`, `aac`, `flac`, `wav`, `pcm`), `speed` (optional `f32`, 0.25-4.0), `instructions` (optional style-control string, the gpt-4o-mini-tts dialect's field; a local Orpheus backend may map it to prompt conditioning or ignore it), and `stream_format` (optional `sse`|`audio`, OpenAI's streaming selector). Follow the crate's existing discipline: a `validate()` method returning structured reasons, mirroring `ChatRequest::validate` at `wire.rs:73`. Two tolerance notes: OpenAI now also accepts `voice` as an object (`{"id": "voice_1234"}`) for custom voices - the gateway validates `voice` as a string against the catalog, but the wire type should not make a future object form unrepresentable; and OpenAI's voice catalog is model-dependent (13 built-ins in 2026, but `tts-1`/`tts-1-hd` support only 9), which is why voice validation belongs to the route and the per-model catalog, never to a shared constant.

One hard rule, because it is easy to break by accident: **never sanitize angle-bracket content out of `input`.** Orpheus's emotion control arrives inline as tags - `<laugh>`, `<chuckle>`, `<sigh>`, `<cough>`, `<sniffle>`, `<groan>`, `<yawn>`, `<gasp>` ([Orpheus README](https://github.com/canopyai/Orpheus-TTS)) - and any HTML-escaping or tag-stripping instinct anywhere in the pipeline silently destroys the feature.

On input length: the 4096-character cap is the wire contract, but the binding local constraint is tokens, not characters - Orpheus trains on 8192-token sequences yet practitioners report quality artifacts past roughly 4k tokens of generated audio without splitting ([practitioner writeup](https://bitbasti.com/blog/audio-streaming-with-orpheus), single source, medium confidence). Long-input handling is conventionally client-side sentence-priority chunking plus stitching, or a server-side async job; this feature's route enforces the cap, and the follow-on conditioning helper (see Risks) owns splitting. Neither the route nor the engine silently truncates.

The response is binary, which is the one place this feature departs from the gateway's typed-relay norm. Chat re-validates and re-serializes every SSE chunk (`crates/gateway/src/lib.rs:551-610`); speech cannot do that - audio frames are opaque bytes. The correct discipline is byte passthrough with header mapping: forward the upstream `Content-Type`, stream the body chunks as they arrive, and treat a mid-stream transport failure as a truncated response, not an error envelope (the client already has partial audio; an OpenAI-shaped JSON error cannot follow 200 + audio bytes). Justify the departure in the handler's doc comment the same way `relay_sse` justifies its design. The content-type mapping is `mp3` -> `audio/mpeg`, `wav` -> `audio/wav`, `pcm` -> `audio/pcm`, `opus` -> `audio/ogg`, `flac` -> `audio/flac`, `aac` -> `audio/aac`; the opus and aac spellings vary across providers and are verified per provider at implementation time.

Two format decisions for the local engine's output, since Orpheus emits raw 24 kHz 16-bit mono PCM (the same rate and layout as OpenAI's `pcm` and Together's `raw`, so no resampling ever happens). For `wav`, emit the standard 44-byte RIFF header with the size fields set to `0xFFFFFFFF` and then stream raw PCM - this is what OpenAI itself streams for wav (hexdump-verified by the speaches project, [issue #493](https://github.com/speaches-ai/speaches/issues/493)), hound emits exactly this header via `WavSpec::into_header_for_infinite_file()`, and RF64 is unnecessary at TTS durations; strict parsers that reject placeholder sizes should request `pcm`. For compressed formats the phase-1 policy is: `pcm` is passthrough, `wav` is header-prepend, `mp3` is stream-encoded (`rusty_mp3` or `glint-audio`; both are young, so spike before committing), `opus` is `ropus` into an Ogg container, and `aac`/`flac` are rejected with a 400 naming the supported set - matching what OpenAI-compatible servers actually stream today.

Add `send_speech` to the `Upstream` trait (`crates/gateway-protocol/src/upstream.rs:44-148`, which also carries a `shutdown` method the new method should sit beside) with the same contract shape as `send_embeddings`: substitute `upstream_model` for the caller's model name, default to `ProtocolError::ModelUnavailable` so upstreams without speech decline rather than fabricate. The return type is a new `StreamedAudio { content_type: String, body: BoxStream<'static, Result<Bytes, ProtocolError>> }` - modeled on `StreamedChunks` (`upstream.rs:21-40`) but byte-typed. `OpenAiUpstream` implements it over the existing raw `post` helper (`upstream.rs:200-229`) using the connect-timeout-only streaming client (`http_stream`, `upstream.rs:156-159`), because a whole-request timeout would kill a long synthesis stream exactly as it would kill SSE. Two refinements to that client for this workload: add a `read_timeout` (30-60 s) - reqwest's per-read idle timeout, which resets on every chunk and so detects a stalled upstream without capping total stream length - and `tcp_keepalive`, so a dead upstream cannot hold a dominion permit forever. On the response side, hyper emits `Transfer-Encoding: chunked` automatically when the body size is unknown: never set `Content-Length` on the stream, and exclude this route from any future tower-http `CompressionLayer` or whole-request `TimeoutLayer`, both of which buffer or kill long-lived streams. The disconnect semantics come free and are worth asserting in tests: when the client goes away, hyper drops the body, which drops the stream, which drops the upstream `reqwest::Response` and aborts the upstream request - the same Drop chain the chat relay relies on.

### 3. Route: `POST /v1/audio/speech`, cloned from the embeddings handler

Register beside the other workload routes in `build_router` (`crates/gateway/src/lib.rs:290-299`):

```rust
.route("/v1/audio/speech", post(audio_speech))
```

The handler is the embeddings handler (`lib.rs:613-646`) with three changes: the kind guard is `ModelKind::Speech`; after queue admission, validate `voice` against the model's `voices` capability when that list is non-empty (400 `invalid_request_error` naming the valid voices on mismatch); and the tail streams `StreamedAudio` into a `Body::from_stream` response instead of returning `Json`. Hold the dominion permit and the `InFlightGuard` across the stream's lifetime exactly as `relay_sse` does (`lib.rs:559-610`): the permit drops when the stream ends or the client disconnects, and `in_flight.cancelled()` terminates the stream mid-flight so profile switches stay atomic. Auth runs before body extraction, matching the transcription handler's ordering rationale (`lib.rs:416-435`).

### 4. Remote passthrough is the phase-1 deliverable

Together AI serves Orpheus 3B in an OpenAI-compatible speech dialect (`client.audio.speech.create(model="canopylabs/orpheus-3b-0.1-ft", input=..., voice="tara")` per their [model page](https://www.together.ai/models/orpheus-tts)). Compatible is not identical, and the differences are documented in their [text-to-speech docs](https://docs.together.ai/docs/inference/text-to-speech/overview): `response_format` defaults to `wav` there (OpenAI defaults to `mp3`), the format enum adds `raw` and `mulaw`, and the request adds `sample_rate`, `bit_rate`, `language`, `response_encoding`, `alignment`, `segment`, and a `stream` flag. Two consequences. First, verbatim passthrough works, but a client relying on OpenAI's mp3 default silently gets wav from a Together-backed model - the gateway should pin `response_format` when the caller omits it, defaulting to mp3 for wire fidelity. Second, Together's streaming is SSE of base64-encoded raw PCM (`stream=true` with `response_format=raw` only), not chunked binary audio - so phase-1 passthrough from Together is non-streaming, and an SSE-decode/reframe path is a fast follow if Together-backed streaming is wanted. OpenAI's own speech endpoint, by contrast, streams chunked binary (`Transfer-Encoding: chunked`), matching this report's `StreamedAudio` design. Together's failure taxonomy also deserves passthrough care: rate limits are dynamic 429s carrying `x-ratelimit-reset`, and capacity failures are 503 - both should map to distinct gateway error codes rather than a generic upstream failure.

With `send_speech` forwarding the request body verbatim apart from the model-name substitution - the same passthrough discipline the gateway applies to chat ("request fields the gateway does not name pass through to the backend verbatim", `guide/src/gateway/10-serving-and-observing.md:69`) - OpenAI `tts-1`/`gpt-4o-mini-tts` and any other OpenAI-shaped speech provider work with zero additional code. ElevenLabs is out of scope, and the divergence is structural, not cosmetic: the voice id travels in the URL path (`/v1/text-to-speech/{voice_id}`), auth is an `xi-api-key` header, the output format is a query parameter, and voice tuning is a `voice_settings` object ([ElevenLabs convert reference](https://elevenlabs.io/docs/api-reference/text-to-speech/convert)). An adapter is a separate feature. Baseten, Canopy's preferred Orpheus host, is likewise not OpenAI-shaped (HTTP `/predict` or a WebSocket with JSON metadata in and binary PCM chunks out) and is documented here only so phase 2 knows the managed-service alternative exists.

### 5. Local Orpheus is phase 2, gated on an engine spike

The blocker, stated plainly: Orpheus emits SNAC codec tokens that a convolutional detokenizer turns into waveform, and the workspace's native stack has no SNAC decode path. The pinned llama.cpp toolchain's TTS support targets OuteTTS's WavTokenizer (a workspace-wide search finds no `snac` or `orpheus` references anywhere in `promptforge/`), and upstream llama.cpp has no merged Orpheus support: [issue #12476](https://github.com/ggml-org/llama.cpp/issues/12476) has been open since 2025-03 with the maintainer explicitly wanting a second codec to generalize around before merging anything, and [draft PR #12487](https://github.com/ggml-org/llama.cpp/pull/12487) stalled in 2025-05. What changed since this feature was first scoped: working native Orpheus runtimes now exist off the shelf, so the question is which integration shape to adopt, not whether one can be built. Likelihood that upstream llama.cpp lands maintained Orpheus/SNAC support on a useful timeline: unlikely; do not plan around it.

Whichever engine lands, the local model launches with a new `ServeMode::Speech` arm beside `Embeddings`/`Reranking` (`crates/gateway-local/src/runtime.rs:550-551`, `crates/gateway-local/src/server/support.rs:326-327`), provisions its GGUF through the existing digest-pinned cache, and counts `vram_gb` against its dominion exactly like every other local model.

### 6. Catalog and clients

`GET /v1/models` surfaces speech models with `kind: "speech"` and the `voices` capability through the existing `ModelInfo` mapping (`crates/gateway/src/lib.rs:684-701`). Alongside it, add `GET /v1/audio/voices`: a trivial route returning the union of the active profile's speech models' `voices` lists as `{"voices": [{"id": "tara", "name": "tara"}, ...]}`. The justification is ecosystem compatibility, not internal need: OpenAI proper has no voice-list endpoint, but the OpenAI-compatible ecosystem has converged on `GET /v1/audio/voices` returning `{"voices": [...]}` - Kokoro-FastAPI, vLLM-Omni, and Fish Audio all serve it, and clients (Open WebUI, Talemate, the blazen-audio-tts crate) probe for it. Serve entries as `{"id", "name"}` objects and document that plain strings are also accepted by tolerant clients: when Kokoro-FastAPI v0.4.0 switched its entries from strings to objects, Open WebUI silently fell back to its hardcoded six-voice OpenAI list ([issue #462](https://github.com/remsky/Kokoro-FastAPI/issues/462)) - entry shape is itself a compatibility surface. Confidence: high that the route is worth its near-zero cost; medium that the object shape is the right canonical form, on the strength of the converging servers.

The Hugging Face admin search already recognizes the `text-to-speech` pipeline tag (`crates/gateway/src/hf.rs:209`, `crates/gateway-config-ui/ui/src/services/hf-api.ts:30`), so model discovery needs no work. Workshop playback (streaming synthesized audio into the webview when an assistant turn completes) is a follow-on consumer of this endpoint, not part of this feature; when it lands, the established low-latency pattern is `response_format=pcm` over fetch's `ReadableStream` into an AudioWorklet port-queue player with a 400-600 ms prebuffer waterline, an MSE `audio/mpeg` sequence-mode fallback, and the WebView2 environment created with `--autoplay-policy=no-user-gesture-required` ([client practice references](https://makerportal.ai/blog/elevenlabs-web-audio-streaming-latency)). The STT socket pattern (`crates/gateway-stt/src/stt.rs:36-53`) is the template if a bidirectional `/tts` socket is ever wanted.

## Implementation plan

Phase 1 is the whole feature minus the local engine; each step is independently testable and lands green.

1. **Config kind.** Add `ModelKind::Speech` with serde/Display spellings; extend kind-field validation; add `voices` to `Capabilities`. Tests: config parse/serialize round-trip, chat-only-field rejection on a speech model, mirroring `crates/gateway-config/src/config/tests.rs` and `config/tests/serialize.rs`.
2. **Wire types.** `SpeechRequest` with `validate()`, `StreamedAudio`, and the `Upstream::send_speech` default in `gateway-protocol`; `OpenAiUpstream` implementation over the streaming client. Tests: request validation table, upstream status/transport error mapping, mirroring the existing upstream tests (`crates/gateway-protocol/src/upstream.rs`, test module near line 970).
3. **Route.** `audio_speech` handler and registration in `crates/gateway/src/lib.rs`; `KindMismatch` coverage; voice-list validation; binary streaming response with permit and in-flight guard held for the stream; the `GET /v1/audio/voices` union route. Tests: a mock backend serving canned audio bytes, asserting auth, kind guard, voice rejection, content-type forwarding, mid-stream cancellation, and the voices-union shape - mirroring the gateway's integration test harness (`crates/gateway/tests/it/support.rs`).
4. **Remote verification.** Manual end-to-end against Together AI's Orpheus endpoint behind a throwaway profile; record the observed request/response dialect (including the `response_format` default and the streaming shape) in the commit message or a design note, because provider docs drift.
5. **Docs.** The gateway README gains a "Speech synthesis models" section beside "Speech-to-text models" (`crates/gateway/README.md:102-134`); the guide gains a chapter beside `guide/src/gateway/05-speech.md` (STT) with a `guide/src/SUMMARY.md` entry, covering the `[[model]]` speech fields, the `voices` capability, the `/v1/audio/speech` request shape, and the `/v1/audio/voices` route.

Phase 2 (local Orpheus) starts only after the engine spike in section 5 returns a verdict: a head-to-head of the CrispASR managed child against the llama-server + in-process SNAC hybrid, scored on TTFA, RTF under concurrent load, and the ASR-roundtrip quality gate. ## Risks and open questions

- **SNAC frame-drop defect (high impact, named and reproducible).** Orpheus can emit SNAC codes outside the valid 0-4095 range, and the reference decoder silently drops the entire frame, skipping words in the output. Canopy acknowledges the bug and it is unfixed upstream ([issue #81](https://github.com/canopyai/Orpheus-TTS/issues/81)); the community fix is slot-constrained logit processors that restrict each of the 7 codebook slots to its 4096-wide token band ([issue #288](https://github.com/canopyai/Orpheus-TTS/issues/288)). The phase-2 spike must verify whether the chosen engine implements slot-constrained logits or inherits the bug - engine choice is a quality gate, not just a feasibility gate.
- **SNAC decode is the concurrency bottleneck (medium).** Measured evidence from a vLLM + separate-decoder deployment shows the SNAC decoder, not the LLM, degrading first under concurrency when colocated on one GPU ([orpheus-streaming issue #5](https://github.com/taresh18/orpheus-streaming/issues/5)). The hard floor is throughput: RTF 1.0 is ~91 codec tokens per second, and streaming stutter is a throughput symptom, not a bug. Capacity planning for concurrent synthesis should budget the decoder, not the backbone.
- **TTFA floor (expectation-setting).** SNAC's non-causal multi-scale decode sets a latency floor, and Canopy's "~200 ms, reducible to ~100 ms" marketing referred to input streaming, not audio-out ([Orpheus-FastAPI issue #46](https://github.com/Lex-au/Orpheus-FastAPI/issues/46)). Realistic TTFA on 24 GB cards is ~150-250 ms (200 ms measured for vLLM-fp16 on an RTX 4090). The Workshop's playback design should treat ~200 ms as the floor, not the target to beat.
- **Sampling stability (low, easily closed).** Greedy decoding is unstable for Orpheus; the working recipe is temperature ~0.6 with top-k sampling and repetition_penalty >= 1.1, and Q8_0 GGUF is ASR-roundtrip word-exact against F16 under that recipe ([cstr's GGUF card](https://huggingface.co/cstr/orpheus-3b-0.1-ft-GGUF)). The gateway should pin speech-model sampling defaults rather than inheriting chat defaults.
- **Compute contention (low on 24 GB).** Three resident GPU workloads share SMs; synthesis during an active authoring-LLM stream can jitter time-to-first-audio. The draft mitigation of pinning the speech child's CUDA stream priority is not actionable on Windows: CUDA stream priorities are per-process, and NVIDIA MPS (the cross-process mechanism) is Linux-only. The actionable mitigations are a priority lane for speech in the existing dominion queue (short, TTFA-sensitive jobs admitted ahead of queued chat work), the client-side 400-600 ms prebuffer, and TTFA instrumentation against the voice-agent industry's 100-300 ms TTS-stage budget. Not a design blocker.
- **Provider dialect drift (partially confirmed).** Together AI's dialect diverges from OpenAI's in defaults and streaming shape (section 4), and drift can be semantic as well as structural: the gpt-4o-mini-tts 2025-12-15 snapshot ignores `instructions` and truncates final sentences while the working 2025-03-20 snapshot is being deprecated ([community report](https://community.openai.com/t/tts-no-longer-follows-instructions-parameter/1371743)). Step 4 of the plan records the observed dialect at implementation time; the residual watch item is OpenAI's undocumented `language`/`format` body fields.
- **License compliance (low effort, easy to miss).** `orpheus-3b-0.1-ft` is tagged Apache-2.0 but derives from Llama-3.2-3B-Instruct, which carries the Llama 3.2 Community License; SNAC is MIT; Voxtral TTS is CC BY-NC 4.0. Redistributing GGUFs through the artifact store inherits those terms - a compliance footnote, not a blocker for this project's use.
- **Voice catalog drift (low).** `voices` is operator-maintained catalog data; a stale list produces a clear 400 naming valid voices, never a silent wrong voice.
- **Technical-text conditioning (accepted, follow-on).** Speech-LLMs degrade on dense code or markup, and the established practice is to condition text before synthesis: strip or summarize fenced code (never read it verbatim), drop or verbalize URLs, verbalize camelCase identifiers and paths, expand symbols, then chunk. Prior art to crib from when the helper lands: wyoming_tts_proxy (markdown/emoji/URL/code-fence stripping plus regex replacements), TextForSpeech (identifier and path verbalization with style levels), and mendelio-voice-text's three-representation pattern (display, spoken, and model text kept distinct, with explicit failure on unknown combinations). Deliberately out of scope for this feature.
