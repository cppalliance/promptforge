## The generator and the assembler

The generator prompt does all model work; the Rust assembler does all deterministic work.

### `tools/document.md` - the guided generator (a frontier-harness tool file)

A customized copy of `tools-public/tools/dokuman.md` living in the promptforge repo - same tag-reference dispatch and subagent discipline, but the pipeline is COMPRESSED (dokuman's own design notes warn that over-specification breeds brittleness; this copy trusts the model and covers the risk with gates):

1. **Recon** (1 fast subagent): structural brief + extraction manifest.
2. **Extract** (1 subagent per manifest file): capability sentences with source/evidence lines. **GATE 1 - full extraction:** the manifest is a contract; main checks every manifest line against a scratch file in `extract/` and the run does not advance until every file is extracted. No sampling, no skipping.
3. **Tier + order** (1 subagent): consolidate, dedup, tier, dependency-order, group into chapters - stated as outcome requirements, not dokuman's four named passes.
4. **Verify the plan** (1 subagent, capped at 300 tokens): coverage, tier accuracy, ordering, noise - before any prose is written.
5. **Evidence packet** (1 subagent): the analytical firewall, UNTOUCHED from dokuman - the narrative packet plus the syntax-details file, both written in STE. The writer never analyzes, only renders; this is what keeps the output out of slop territory.
6. **Write** (ONE subagent per set): voice consistency requires a single author, and the author is the mentor - "kind, patient mentor teaching a student; start small and easy, build up step by step, logically connected paragraphs and sections" - writing with the prose-rulebook's discipline (no meta-announcements, capped machine idioms, real actors) and dropping into STE for procedural content. Splits by whole chapters only when the evidence packet exceeds one context, never mid-chapter; every split writer receives the same packet, details, and template. **Checkpointing:** the writer never produces a large output in one generation - it appends to `drafts/<chapter>.md` in chunks of at most 100 lines, so a timeout loses at most the in-flight chunk. A draft is complete only when its final line is the end marker (`<!-- end -->`); a draft without the marker is partial, and a re-run reads it and continues appending from its last line. The reuse rule keys on the marker, not mere file existence.
7. **GATE 2 - thoroughness verification** (1 subagent per generated chapter file, AFTER writing): each generated markdown file is checked against the tiered list and evidence lines for its chapter - every assigned item covered, examples grounded in real syntax, nothing invented, the mentor voice holds (small-to-big progression, connected paragraphs, no unexplained jumps), the prose-rulebook red flags are absent (no meta-announcements, idiom rates within caps), STE holds in procedural passages, house rules. Returns approve or a correction list; corrections apply and re-check, capped at three rounds; a chapter still failing after three rounds blocks the set and surfaces to the user.
8. **Audit** (main): seams across chapters, links, template completeness.

Compressed, not de-fanged: the anti-slop machinery (manifest contract, evidence lines, the packet firewall, single writer, verify) all survives. What leaves: the Tool Design essay, the images, the flavor, the token-economy scaffolding (one rule replaces it: subagents return paths and counts, bodies live in scratch), the intake ceremony (the lens IS the scope), consolidate as a separate step (a shell concat plus one dedup sentence), the four-pass tier procedure (outcome statements instead), and the runtime template choice (each lens block carries its set's template shape). Target size: dokuman.md is ~330 lines; this copy lands around 150-180.

Three more adaptations define the copy:

**Stripped.** The copy is operational content only - pipeline, rules, tag blocks; the compression list above already removed the essay, images, and flavor.

**Registers by layer.** The tool file itself and the evidence layer (packet and details) are written in ASD-STE100 Simplified Technical English: short sentences, one instruction per sentence, active voice, approved general vocabulary. The STE escape hatch is declared explicitly in the tool: product vocabulary (PromptForge, gateway, workshop, crate names, config keys, host-call names like `models.chat`) is approved technical vocabulary - STE's technical-names category. The written output (chapters, the introduction) carries the mentor identity verbatim in the writing-discipline block: "You are a kind, patient mentor teaching a student the material. You start small and easy and build up step by step in logically connected paragraphs and sections." On that base, the writer adopts the prose-rulebook's revision discipline as it writes - no meta-announcements, machine idioms within the rulebook's caps, real actors named - and drops into STE where the content is procedural (operator steps, install instructions, anything the reader executes verbatim). STE makes the evidence unambiguous; the mentor voice makes the book worth reading; the rulebook keeps the prose human.

**Prompts-rulebook authored.** The tool file is model-read instruction text, so it is WRITTEN under `tools-public/rulebooks/prompts-rulebook.md` - its protocol governs the authoring (specify, structure, examples, voice, budgets, outcomes over procedures), not only a post-hoc audit - and checked against its checklist before the first run. Two of its rules the plan pins here because the tool must carry them: the tool ships an emission-discipline block (generated chapters never name the tool, the rulebooks, or the pipeline - every constraint appears by substance only, and the tool's generation checklist confirms it), and main renders `template.md` from the lens block's template shape before the write stage begins (every pipeline artifact is commanded into existence, never just referenced).

The lens system:

- Five lens blocks, one per set plus `intro`: `<lens-workshop>`, `<lens-gateway>`, `<lens-language>`, `<lens-agent>`, `<lens-intro>`. Each lens block carries: target paths/globs, extraction guidance (what counts as a capability for this audience, what is noise - "UI capabilities, never Rust API" for workshop; "config keys and operation, never Rust API" for gateway; and so on per the sets table), the audience, and the output directory.
- The dispatch gains one run variable: the lens tag name. The recon and extract tasks receive the lens block's guidance; the extract subagent's selection criterion is replaced by the lens's (dokuman's default is "first three minutes of a demo" - the lens overrides with the audience-specific rule). Dokuman's extraction is already user-facing-only by design; the lens does not add that filter - it answers "which user," so a config key surfaces for the operator, a public function for the integrator, and a wire type for no one.
- Lenses filter capabilities, never files. The manifest covers every source file in the lens's targets and gate 1 holds; a file with nothing for this audience yields an empty or near-empty extraction. The empty extractions are the completeness proof - excluding files would silently un-examine them.
- **One tool file rebuilds the entire book.** Run with a lens name, it regenerates that one set. Run with no lens (or `all`), it runs the full pipeline for the four sets in audience order, then the `intro` lens, then invokes the assembler itself (`cargo run -p build-user-guide`) as the final step - SUMMARY.md, the landing pages, and the single-file exports included. The reuse rule makes a re-run cheap (existing scratch skips stages; the assembler still re-runs deterministically); deleting `guide/scratch/` forces a full rebuild from zero. This is the end-state property: the entire documentation set regenerates from one markdown prompt.
- The tier step's named section grouping becomes the set's CHAPTERS. Writing follows pipeline step 6 (ONE writer subagent per set; whole-chapter splits only under context pressure, same packet and template throughout); the audit step checks seams, syntax, grounding, and voice consistency across chapters, and enforces the house rules: no em-dashes, four-backtick fences.
- Output: chapter files written to `guide/src/<set>/`. The `intro` lens (step 7) writes `guide/src/introduction.md` - synthesis, not extraction. Its evidence source is `design/what-promptforge-is.md` (the pipeline creates evidence from it and never modifies it - step 1's revision is the only edit that file gets) plus the four sets' checked-in chapters for audience routing. The writer's discipline gains two instructions: explain what all the moving parts are - the engine, the gateway, the workshop, the library - so a reader finishes the introduction knowing the system's pieces and which set teaches theirs; and a hard size limit - the introduction is at most 60 unwrapped lines (each paragraph one line, per the house md convention), and gate 2 rejects anything longer. Step 1 generalized the design doc, so the intro speaks in product-level roles; gate 2's no-deleted-products check remains as insurance. The lens runs a REDUCED pipeline, declared in its block: no extract and no tier (nothing to mine) - recon inventories the design doc and the checked-in chapters, the evidence step maps the thesis and the moving parts to the four audiences, the writer produces the introduction, and gate 2 verifies it like any chapter. Its scratch lives in `guide/scratch/intro/`.
- Scratch layout (all under the gitignored `guide/scratch/`, predictable names so runs resume and reuse): `guide/scratch/<set>/recon-brief.md`, `manifest.txt`, `extract/<file-slug>.md` (one per manifest entry), `tiered.md`, `evidence-packet.md`, `evidence-details.md`, `template.md`, `drafts/<chapter>.md`, `verify/<chapter>.md` (gate 2 verdicts). **Reuse rule: existence-based.** A stage whose scratch output already exists reuses it and skips its subagents; to force a stage to re-run, delete its file. Drafts are the exception: a draft counts as existing only when it ends with the `<!-- end -->` marker (the writer checkpoints every 100 lines, so a partial draft means a timed-out run - it resumes, not restarts). Deleting `extract/<one-file>.md` re-extracts one source file; deleting `tiered.md` re-tiers from the existing extractions; deleting a `verify/<chapter>.md` re-verifies one chapter; deleting the whole `<set>/` directory regenerates the set from scratch. No timestamps, no staleness logic - the file system state is the checkpoint state.

### `build-user-guide` - the assembler (Rust crate, repurposed not deleted)

The crate keeps its renamed form from the rename plan and gains the book-assembly job: walk `guide/src/<set>/` directories, regenerate `guide/src/SUMMARY.md` (the table of contents linking every interior page, parts in audience order: workshop, gateway, language, agent), concatenate each set's chapters into `guide/promptforge-<set>-guide.md` single-file exports, and verify every SUMMARY link resolves to a checked-in file. Pure deterministic Rust with unit tests - no model client, no gateway dependency. It owns `SUMMARY.md`; the generator's `intro` lens owns `introduction.md`; neither file is hand-edited.

## Recovered rationale

# Enrichment: product user guides (b2c7ec0c)

Source: creator chat d2fad42b (Aug 29 - Sep 2, 2026; the docs discussion is Sep 2, 4:27 PM - 6:51 PM), run chats 4987e731 and 76401aea. Verbatim user quotes are quoted; everything else is paraphrase.

## Why the plan exists

The old documentation was structurally wrong, not just stale. The user: "Want to delete all the users guides... cause they're wrong. There should not be a user guide per crate. There should be a user guide per product." Per-crate guides fragment the story along implementation boundaries the reader does not care about; the reader cares about the product they hold. This is the root decision everything else follows from.

A second motive is maintenance drag. On deleting the old design docs (step 0): "they are out of date in places and the rationale can always be re-excerpted from the code. it feels like this is just a drag on maintenance because it goes out of date by definition with any meaningful work." The same logic produced step 1: "the plan should edit down what-promptforge-is to general terms so that any current or future implementation drift does not affect the doc." Documentation that restates implementation detail is a liability; documentation that states roles and principles survives refactors.

## Design thinking

**Guided extraction (the lenses).** The user rejected unguided dokuman runs: "the gateway guide has to be all about the configuration, what's in the UI, what can be configured... we don't want public APIs, we don't want the Rust functions, but then for the library guide, we do want the Rust functions." Same repo, different audiences, different signal. The lens is the mechanism that makes one pipeline serve four audiences. The user's own lens list: "gateway: server operator configuring things / workshop: a user who is experiencing the user interface / promptforge: a user who is authoring promptforge prompts" (the agent-programs set was added from the parallel agent-harness work; the Rust API set was dropped to rustdoc).

**Full visit, empty extractions as proof.** When the planner tried to scope the gateway set down, the user corrected it twice: "we still visit every source file, and extract the user-facing feature. its just that for most of those files, the user facing feature will be 0 or 1 things" and "I thought dokuman.md made clear that the extraction only extracts user-facing things?" Skipping files silently un-examines them; an empty extraction is an auditable "we looked."

**Compress, but keep the anti-slop spine.** The user asked to "simplify our version of dokuman.md if possible. compress. let the model breathe. but we also need a gate I want a full extraction. and there needs a verification pass after, using a subagent, which makes sure each individual generated markdown file is THOROUGH." When the planner compressed too far: "oh no you got it wrong. the evidence packet and separate subagent writer discipline is what makes the tool's output not ai-slop!" So: everything negotiable except the analytical firewall (evidence packet) and the single-writer separation.

**Voice and register.** "the evidence is written in ASD-STE100 and the writing is done using 'You are a kind, patient mentor teaching a student the material. You start small and easy and build up step by step in logically connected paragraphs and sections.'" And the tool itself: "stripped of flavor and images, use ASD-STE100 register both in the tool and in the generated docs."

**Checkpointing.** "during writing, the writer must checkpoint every 100 lines to prevenet timeouts" - the origin of the chunked-draft, end-marker reuse rule.

**Scratch in-repo.** "the scratch files should go into a gitignored directory within the promptforge repository directory, and the scratch files should have predictable names so they can be reused" - a deliberate exception to the cabinet scratch rule, for inspectability and re-run reuse.

**One-command rebuild as the deliverable.** The user checked the intent twice: "is it clear that the plan will leave behind a single markdown prompt which rebuilds the entire documentation set, by rebuilding the dokuman docs for each product, writing an intro, and then using the rust program to assemble it?" and "is it clear that the plan will leave behind the tools to regenerate the docs every time as needed?" The docs are a product of the tool; the tool is the real deliverable.

**Storefront.** "the README.md should feature prominent evergreen download links for the major platforms" and "for Step 9 preserve the existing images. Keep them where they are, just rewrite the text in between them." On buttons: the user first imagined "three beautiful buttons, a gateway button, a workshop button, and whatever the other thing is," then concluded "I think it's just a workshop. We really need the, we really need the workshop. We should only offer the workshop and the other ones they can get... they can download it individually." Hence the workshop as the single prominent download.
