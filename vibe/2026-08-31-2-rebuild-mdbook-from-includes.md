The included content is compiled as markdown by mdBook, so headings, code fences, and links all work.

# Enrichment: Rebuild mdBook from includes

## Why (creator chat)

The mdBook's 15 chapters were hand-written in a single commit on 2026-08-12 (almost certainly one agent session) and never touched again. By Aug 31 they were stale: they reflected the pre-profile, pre-STT, pre-template state of promptforge. Meanwhile the same chat's Step 10 had just regenerated 10 per-crate user guides via the dokuman pipeline, and those were current. The user no longer remembered how the book had been produced: "I don't remember. how do you suggest we rewrite it?" The underlying intent (paraphrase): stop maintaining two diverging documentation layers by hand; make the book track the per-crate guides automatically.

The assistant treated this as an architecture decision, not a mechanical task, and switched to plan mode: "This is a documentation architecture decision with multiple valid approaches - plan mode to discuss trade-offs before executing."

## Discarded alternatives

The user was offered four options for what the mdBook should become and picked the first (marked Recommended):

1. CHOSEN - Replace the hand-authored chapters with `{{#include}}` directives pulling from the per-crate user guides.
2. Discarded - Run dokuman again to regenerate the mdBook chapters directly, deleting the old ones. (Would produce a fresh but still separately-generated book, free to drift stale again.)
3. Discarded - Delete the mdBook entirely and make the assembled flat guide (`make-user-guide` output) the only documentation product.
4. Discarded - Keep both products but rewrite the mdBook chapters to match current state. (One-time fix; same staleness problem returns.)

The design thinking behind the chosen option, verbatim from the assistant: "the per-crate guides are the source of truth, and `{{#include}}` makes the mdBook a thin assembly layer that stays current automatically." Chapter consolidation (15 topic chapters down to 11) falls out of the mapping, since each per-crate guide is already a coherent document.

## Decisive user statements (verbatim)

- "I don't remember. how do you suggest we rewrite it?" - delegated the approach choice.
- "are you going to delete the outdated files?" - confirmed the stale chapters should be removed, not left alongside.
- "prepare the plan for a fresh context" - the plan had to be fully self-contained (every include path, every deletion, the verification command) so a fresh agent could execute it without the conversation history.

## Deviations during the run

The run chat executed the plan as written; all deviations were forced by verification, not by design changes:

1. **`<path>` HTML warning.** `mdbook build` warned that `<path>` inside quoted error-message examples in the CLI guide parsed as an unclosed HTML tag. The plan said "No changes to the per-crate guides", but it also required zero warnings, so the runner code-spanned the quoted examples in `user-guide-promptforge-cli.md` (a content-neutral formatting fix to the source).
2. **`mdbook test` failures.** The plan assumed the test would be trivially green ("unlikely" Rust fences in operator docs), but untagged code fences are treated as Rust by rustdoc. The runner tagged fences in three source guides: `console` for CLI shell sessions, `markdown` for the core guide's 16 prompt-file examples, `text` for webfetch tool output. Two scripting hiccups (PowerShell backtick escaping collapsed four-backtick fences; a toggle script mis-tagged closing fences in webfetch where tagged and untagged fences are mixed) were caught and repaired before the final build.
3. **Flat guide regenerated.** Because the per-crate sources changed, the runner re-ran `make-user-guide` to keep the two views in sync, consistent with the plan's stated philosophy even though the plan said the flat guide was unchanged.
4. **Deletion mechanism.** The runner used `git rm` for the stale chapters (recoverable from git history) rather than the Delete tool, reconciling the workspace no-delete rule with the plan's deletion instruction.
5. **mdBook not installed.** Installed 0.5.4 via `cargo install` in the background while doing the file work, as the plan allowed.

Runner's retrospective on the plan (paraphrase): data flow was sound (all 10 per-crate guides existed, include paths correct) and the step breakdown was efficient; the only gaps were the two verification assumptions above, and a dry-run `mdbook build` during planning would have surfaced both.

Note: after the plan completed (commit `7579e2c`, 25 files, +72/-2849), the run chat drifted into an unrelated crates.io publishing discussion; nothing in it bears on this plan.
