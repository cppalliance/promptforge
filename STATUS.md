# PromptForge Status

## What exists and works

Gateway v0 complete. Two-process vertical slice: `promptforge run` -> the gateway
(which holds the vendor key) -> the backend -> "Hello, world!". The executor no
longer holds any vendor credential, only the gateway URL and shared token.

- `promptforge-core::parser` - frontmatter + H1/description + recursive H2-H6 tree + leading Lua-fence separation. 10 unit tests.
- `promptforge-core::client::GatewayClient` - OpenAI-shaped client pointed at the gateway (URL + shared token; no vendor key). `DEFAULT_MODEL` is public, so a caller configured from a file rather than the environment shares the one fallback instead of spelling its own.
- `promptforge-core::execute::run(prompt, args, tools, store, opts)` - walks top-level sections in file order, each in a fresh context; a Lua `return` finishes the run early, otherwise prose (if any) takes one round trip and control falls through to the next section. Running off the end yields `default_return`, else the last reply, else a generic completion. `opts` is `RunOptions { observer: &dyn Observer, client: Option<GatewayClient> }`: `client: None` builds the client from the environment (the CLI's path), and `Some(..)` is how a caller configured from a file supplies one, since setting an env var is `unsafe` under edition 2024. 28 unit tests, in the child module `execute/tests.rs` (Lua-only and offline except the mock-gateway ones).
- `promptforge-core::observe` - the progress-reporting seam: the `Observer` trait (`Send + Sync`, one synchronous `on_event`), the `#[non_exhaustive]` `Event` enum (`RunStarted`, `SectionStarted`, `SectionFinished`, `ModelTurn`, `ToolCalled`, `RunFinished`; externally tagged serde, `PartialEq`), and `NullObserver`, which discards. 5 unit tests, one of them an exhaustive `match` over `Event` so a variant added later breaks the build until the test data covers it.
- The executor emits through that seam. A run that clears the version gate reports `RunStarted` (prompt name + declared section count), then per section `SectionStarted` (`completed` = sections entered, 1-based, never decreasing) and `SectionFinished` - including for the section a Lua `return` ends the run in - and finally `RunFinished` (run-wide turn total, elapsed ms, `ok`) however it ends, error included. A run the gate refuses reports nothing: it never started. Inside a section's tool loop, every round trip that produced a reply is one `ModelTurn` (numbered within the section) and every dispatch is one `ToolCalled` carrying `ok`, so a tool that fails is reported before the error propagates. Events are a side channel: dropping them cannot change a run's result, which is what lets `NullObserver` be the default.
- `promptforge-cli` - `promptforge run <file.md>`.
- `promptforge-tool-picker` - in progress. Will become a pure, deterministic, embedding-based engine that resolves a plain-English capability need against an abstract tool catalog (no Lua, MCP, or network). Done: `catalog` - `ToolId` (the `(server, name)` pair, compared as a pair; `qualified_key()` joins with U+001F, which cannot occur in either part), `ToolAnnotations` (optional MCP hints), `ToolDescriptor`, `Catalog` (serde; JSON array of flat MCP-shaped objects), and `enriched_text()` = name + description + top-level `properties` keys sorted ascending for determinism. `config` - `ModelId` (non_exhaustive; v1 has only bge-small-en-v1.5, since only its weights are embedded) and `Config` (serde, every field optional) with justified defaults: `similarity_floor` 0.825 (5% false-bind budget), `duplicate_threshold` 0.98, `top_k` 3, `margin` 0.05 (provisional, not measured); `Config::validate()` rejects NaN or out-of-`0.0..=1.0` thresholds and `top_k` 0, and checks no relation between thresholds: `duplicate_threshold` measures one tool against another while `similarity_floor` measures a need against a tool, so neither bounds the other. `error` - `Error` (thiserror, non_exhaustive) + `Result<T>`. `assets` - the model is compiled into the library: `build.rs` fetches BAAI/bge-small-en-v1.5 via `hf-hub` (blocking) pinned to commit `5c38ec7c`, verifies each file against a hardcoded SHA-256, downcasts the fp32 safetensors to fp16 (133MB -> 67MB, bit-exact round-to-nearest-even; the lone I64 tensor passes through), and stages weights + `tokenizer.json` + `config.json` in `OUT_DIR`, which `include_bytes!` embeds. fp16 is a storage choice only - the loader picks the compute dtype. Nothing model-related is git-visible. First build needs network; later builds use the HF cache, and a stamp file in `OUT_DIR` skips the work. Both failure paths (bad digest, cold cache offline) abort with an actionable message. `embed` - `Embedder` (Send + Sync, manual Debug) loads the compiled-in model once in `Embedder::new` (Candle `VarBuilder::from_buffered_safetensors`, upcast fp16 -> f32 since `include_bytes!` data is 1-byte aligned and Candle's f16 CPU coverage is uneven; `Tokenizer::from_bytes`, truncate at 512, never pad) and `embed(&self, &str) -> Vec<f32>` returns a 384-dimension CLS-pooled, L2-normalized vector. No query prefix: needs and tool texts take the identical path, which is what the study's thresholds were measured under. `embed_all` is a loop, not a batch, so a vector never depends on its neighbours. Failures land on `Error::ModelLoad` / `Tokenize` / `Embed`, each carrying a detail string rather than a dependency's error type. `picker` - `ToolPicker::build_with(Arc<Embedder>, Catalog, Config)` is the one indexing path: it validates the config, then embeds every tool from its `enriched_text()` with an encoder the caller already loaded. `build(Catalog, Config)` is a thin wrapper - it validates first, so a bad threshold still costs no model load, loads one `Embedder`, and calls it - and `rebuild(&self, catalog)` calls it with this engine's own encoder and configuration, so a changed catalog costs one forward pass per tool and no weights (which is what the MCP server's save-time rebuild rides). A rebuild carries the configuration over because it is a change of data and not of policy; a caller changing a threshold hands `embedder()` back to `build_with`. The encoder is `Arc`-shared rather than owned outright, so several engines over different catalogs hold one set of weights; sharing cannot change an answer, since two engines over one encoder embed identical text to identical vectors, and the test that a rebuild skips the loading path is an `Arc::ptr_eq` identity check rather than a wall-clock comparison, which would measure the machine. Vectors live in one flat contiguous `Vec<f32>` at a 384 stride, one row per tool in catalog order, all unit-norm, so a later cosine is a plain dot product; no persistent cache, memory only. An empty catalog builds rather than erroring - abstention is already an outcome, and a runtime-assembled catalog is legitimately empty. Accessors: `len`/`is_empty`, `tools()`, `config()`, `vector(index)`. `rank` (crate-internal, not public API) - `top_k(query, vectors, k)` scores every row by dot product (both sides are unit-norm, so that is the cosine) and returns `Candidate { index, score }` best first. The sort key is a total order - score descending via `f32::total_cmp`, then catalog position ascending - so a ranking is a function of its inputs even when scores tie exactly; catalog position is the tie-break because it is the only key guaranteed unique (identities may legitimately repeat across servers). A non-finite score orders as the worst possible but is reported as computed; `k` beyond the catalog returns the catalog unpadded; a zero `k`, an empty index, or an empty query returns nothing; truncation is under score-then-position alone, so a candidate a later re-sort would promote is already gone if it missed the cut. `rank::Vectors` is a borrowed view of the flat buffer (`row(i)`, `similarity(a, b)`) that lets the policy compare two tools to each other. `ToolPicker::rank(need, k)` embeds the need and ranks, deciding nothing. `policy` - `Outcome` (public: `Bind(ToolDescriptor)` | `Duplicate(Vec<_>)` | `Ambiguous(Vec<_>)` | `Absent`) and the crate-internal decision function over a ranking + the catalog + the stored vectors + the config. Precedence, first match wins: (1) `Absent` when the top score is below `similarity_floor` - if nothing fits, twin-ness is irrelevant; (2) `Duplicate` when at least one other candidate shares the leader's server and its stored vector is at or above `duplicate_threshold` similar to the leader's, ahead of the margin test so a narrow margin cannot silence a fault; (3) `Bind` when the leader beats the runner-up by at least `margin` (a runner-up above the floor does not weaken it); (4) `Ambiguous` for any remaining near-tie, whatever servers it spans. A twin is a property of the pair of tools, not of their scores: the threshold is the cosine between the two tools' own unit-norm embeddings, so it is the same whatever need is asked, and the duplicate group is not filtered by score. Same-server vs cross-server IS the Duplicate/Ambiguous split, since a descriptor carries no "own vs imported" flag - one server's twin pair is somebody's fixable config error, a cross-server collision is the caller's own intended union. All three thresholds are inclusive (at the floor is considered, a gap equal to the margin binds, a pair exactly at the duplicate threshold is twins); shortlists carry `top_k` candidates but never fewer than two, and `decide` ranks `top_k.max(2)` so a `top_k` of 1 cannot hide a runner-up. Annotation tie-break: among *exactly* equal scores only, prefer `read_only: Some(true)`, then `destructive: Some(false)`, then `idempotent: Some(true)` - a positive claim promotes, and silence is not a claim, so equal or absent hints leave catalog order intact; treating absence as neutral-if-both-present would be intransitive and forfeit determinism. Hints never overturn a score decision: they cannot promote a near-tie to a `Bind` nor rescue a `Duplicate`, and they only reorder the ties that survived truncation - a hint-preferred tool past position k was dropped by the ranking, not demoted by the policy. Public surface, complete: `ToolPicker::resolve(need) -> Result<Outcome>` wires ranking to policy end to end, and `ToolPicker::shortlist(need, k) -> Result<Vec<ToolDescriptor>>` reports the same ordered candidates without judging between them. An abstention is `Ok(Outcome::Absent)`, never an `Err` - an error means the engine could not run (tokenize / forward pass), not that nothing matched. `shortlist` applies `similarity_floor` and nothing else, so it is empty in exactly the cases `resolve` abstains; a caller wanting near-misses lowers the floor, which is the dial for it, rather than getting a different answer from a different method. `k` is authoritative and is not clamped against `Config::top_k` (which bounds only the shortlist a resolution reports): `k` past the catalog returns what there is unpadded, `k` of 0 returns nothing. No `#[allow]` remains anywhere in the crate. Only `assets` is a public module; `catalog`, `config`, `embed`, `error`, `picker`, and `policy` are private behind the `pub use` facade in `lib.rs`, so every public type has exactly one path, and the four-outcome contract that was the `policy` module's documentation now lives on `Outcome` where a caller can read it. `QUALIFIED_KEY_SEPARATOR` is re-exported from the root, since `qualified_key`'s documentation tells callers to split on it. 99 unit tests + 12 integration tests through the public API only + 7 doctests, including a golden vector, a compile-time `Send + Sync` assertion for both `Embedder` and `ToolPicker`, and exact-boundary policy cases on synthetic scores and synthetic stored rows. `tests/fixtures/mixed-servers.json` is a committed five-tool catalog over four servers - one tool with nothing like it, one server's two names for one capability carrying the same description word for word, and one capability published by two servers - and `tests/it/behavior.rs` loads it through the public serde support via `include_str!`, so no path leaves the crate, and provokes all four outcomes from that prose alone at the default thresholds: a weather need binds, the calendar pair is `Duplicate` (their own embeddings sit at 0.983, over the 0.98 default), the two file tools are `Ambiguous` (0.900 vs 0.875, inside the 0.05 margin), and a translation need is `Absent`. It also pins determinism across the whole pipeline: two builds from one fixture yield identical vectors, outcomes, and shortlists, and repeated calls do not drift. Measured finding: whether a copy-pasted pair is caught depends on how much prose dilutes the differing name - the same two verbatim descriptions under shorter names sit at 0.960, below the default threshold. Both integration areas share one test binary at `tests/it/main.rs`, so the 91MB of embedded weights is linked once instead of twice. Suite runs in about 29s (model load dominates; the integration binary's own 10s is three loads - the determinism rebuild and the one the shared-encoder test holds). `design-tool-picker.md` is the crate's design document and is current.
- `promptforge-mcp` - in progress. Will publish prompts to an agentic harness (Cursor, Claude Code) as callable MCP tools, some direct and the rest behind built-in listing/retrieval tools, over streamable HTTP and stdio. Done: the crate skeleton and `config` - `prompts.toml` parsing with the `Secret` newtype and `${VAR}` interpolation mirrored from the gateway (a third copy would justify lifting it into a shared crate; two does not), and `ConfigError` (thiserror, non_exhaustive: `Read`, `Parse`, `EmptyToken`, `UnresolvedVar`, `Interpolation`). `Config` = `[server]` (`bind` default 127.0.0.1:9310, `token` required and refused if empty or whitespace alone, `max_concurrent_runs` NonZeroUsize default 4 so a zero is a parse error rather than a deadlock, `admission_timeout` 30s, `reply_deadline` 240s - inside Cursor's ~300s call wall with margin, `retain_completed` 1h, `watch` true, `watch_debounce` 500ms; durations are humantime strings) + `[paths].prompts` (default `prompts`) + `[gateway]` (`url`, `token`, optional `model`) + `[catalog]` (`include`/`exclude` globs, `default_expose`) + a `BTreeMap` of `[prompts.NAME]` blocks (`expose`, `enabled` default true, `file`). `Expose` is `tool` | `list`, defaulting to `list`, since direct exposure is a promotion a client only sees after a restart. Every table is `deny_unknown_fields`, so a misspelled key fails the load instead of being ignored. Only `[server]` and `[gateway]` are required; a config with neither `[catalog]` nor `[paths]` parses and enumerates by hand. Interpolation is factored as `interpolate_with(input, lookup)` so tests drive it without setting an environment variable, which edition 2024 makes unsafe. `catalog` - `Catalog::resolve(&Config, OnBroken)` is the single resolution pass, run by boot today and by the watcher later: expand `[catalog].include` (glob crate, `require_literal_separator` so `*` stops at a separator and `**` crosses one), subtract `exclude` (matched against the path relative to the prompts directory, so `drafts/**` reads as it looks), then apply the `[prompts.NAME]` blocks - `file` reaches a prompt no glob matches, `expose` promotes or demotes, `enabled = false` drops. Checks: a glob-matched file declaring no `promptforge:` version is not a prompt and is skipped in silence, every other resolved file must be readable and parse and yield a name matching `^[a-z][a-z0-9_]{0,47}$` (checked, never transformed - a transform would let two frontmatter names collide in `tools/list`) that is not one of the four built-in names, since dispatch answers a built-in first and such a prompt could never run (the broken entry falls back to the file stem, so a retained one cannot publish a second tool under the built-in's name, and `need_prompt` is reserved whether or not the `picker` feature publishes it), a `file` block's frontmatter name must equal its table key, a block with no `file` matching no globbed prompt is a stale override, two prompts declaring one name fails naming both files, an empty catalog fails. Faults accumulate: `CatalogError` carries a `Vec<Fault>` (each naming the prompt and the path where known) and its `Display` prints the count then one line per fault. `OnBroken` is the *only* difference between boot and reload, and it is the consequence rather than the checks: `Reject` turns a prompt's own validation failure into a fault, `Retain` leaves it as an `Entry` whose `problem()` carries the error (`prompt()` is then `None`, name falls back to the block key or the file stem). A catalog-level fault (stale override, duplicate name, bad pattern, empty) stops both. `Entry` accessors: `name`/`description`/`version`/`path`/`expose`/`is_direct`/`prompt`/`problem`/`embed_text` (name with underscores as spaces, `. `, description - mirrors what the picker embeds). `Catalog`: `entries` (ordered by name, then path, so a resolve does not depend on the filesystem's enumeration order), `len`/`is_empty`/`find`/`hash`. `hash` is a content hash over every entry's name and description - what will tell a reload whether a save changed anything retrieval ranks on, so a body-only edit skips the picker rebuild; an in-process comparison value, not a persisted one. `CatalogHandle` holds it in an `ArcSwap`: `load()` hands out an `Arc<Catalog>` snapshot a run in flight keeps across a swap, `store()` replaces it. 32 unit tests + 2 doctests, filesystem ones on `tempfile::TempDir`. `tools` - `tool_definitions(&Catalog) -> Vec<rmcp::model::Tool>` is the whole MCP surface: each `expose = "tool"` entry in catalog order (name and description verbatim from frontmatter, input schema the one optional string `args` since a run takes a single raw argument), then the built-ins. A broken direct entry keeps its tool, described `unavailable: {problem}` - dropping it would remove it from a list every connected client has already cached, so the call arrives anyway with nothing having warned the model. The built-ins are one array in `built_in_tools`, each row pairing the definition with the rule that publishes it, so a fifth is a row and not an edit in three places: `list_prompts` (no arguments) and `run_prompt` (`prompt` + optional `args`) when any prompt is `list`, `need_prompt` (`capability`) under that same rule and `cfg!(feature = "picker")` - a runtime-shaped condition rather than a `#[cfg]`, so the array keeps one length - and `check_run` (`run_id`) whenever anything is published at all, since a direct call can outlive `reply_deadline` too. Publication is a property of the catalog, never of the request, and `publishes_built_in(&Catalog, name)` reads that same array for the dispatcher, so a built-in missing from `tools/list` is one the handler refuses too. `run_prompt`'s description sends a caller unsure of a name to `list_prompts` rather than guessing, and `need_prompt` carries the author-register instruction and both examples twice, in its own description and in the `capability` parameter's, from one `capability_register!` literal so the copies cannot drift; only the definition text is here, the picker itself is step 12. Names are re-exported as `LIST_PROMPTS` / `RUN_PROMPT` / `NEED_PROMPT` / `CHECK_RUN` for the dispatcher to match on. 7 unit tests + 1 doctest, the first of them a golden over `src/tools/tests/golden-tools-list.json`: the full serialized `tools/list` for a two-direct-one-listed catalog, so a reworded description cannot pass unnoticed. `rmcp` is pinned at `=3.1.0` (features `server`, `schemars`, `transport-streamable-http-server`, all three confirmed present on that version), and `promptforge-tool-picker` is optional behind a default-on `picker` feature, so `--no-default-features` builds without the 67MB of embedded weights. `result` - `RunResult` (serde + `JsonSchema`; `run_id`, `prompt`, `version`, `status`, `value`, `turns`, `elapsed_ms`, `error`) and `RunStatus` (`running` | `completed` | `failed`), plus the text block each status carries: the value on completion, the error on failure, a collect-by-id line while running. `server` - `PromptForgeServer::new(Arc<Config>, Arc<CatalogHandle>)` and the `rmcp::ServerHandler` impl. `list_tools` answers from `tool_definitions` over the loaded snapshot; `get_info` advertises tools + `list_changed` and carries session instructions telling a caller to take a name from `list_prompts` rather than guess. `dispatch(CallToolRequestParams) -> Result<CallToolResult, ErrorData>` is the whole of `call_tool` without a transport around it, which is what the tests drive. It routes: `list_prompts` (name / description / version / direct / problem per entry, pretty JSON in the text block and `{prompts: [..]}` in `structuredContent`), `run_prompt` (resolve then run), `check_run` (the run registry answers it; an unknown or evicted id is `isError: true` naming the retention window rather than a protocol fault, since a model that polled too late should learn that) and `need_prompt` (published in step 5, answered in step 12 - it returns `isError: true` saying so, since the tool was advertised and the caller did nothing wrong), a direct prompt's own name, and anything else as `-32601`. Each built-in arm is guarded by `publishes_built_in`, so a name this catalog does not offer - the listing tools over an all-direct catalog, `need_prompt` without the `picker` feature - falls through to `-32601` rather than being answered off the list. Name resolution (`server::resolve`) folds case and treats `-` as `_`, then matches exactly; a miss or an ambiguity runs nothing and returns `isError: true` listing every enabled name closest first by Levenshtein distance, since the model is the only thing that can correct its own guess. Argument extraction is the `-32602` line: a missing or non-string `prompt`, or a non-string `args`, is the client's bug; a missing `args` is the empty string. `server::bind` mirrors ~20 lines of the CLI's `tools.rs` to turn frontmatter tool names into instances (`web_fetch` local, `web_search` on the configured gateway, an unknown name failing the run) and builds the `GatewayClient` from `[gateway]`, falling back to the now-public `promptforge_core::client::DEFAULT_MODEL` when the config names no model. A run gets a fresh `Store::memory()`, a fresh 128-bit hex `run_id`, an `McpObserver`, and `RunOptions { observer, client: Some(..) }`; `elapsed_ms` is measured from admission rather than from the request, so a queue wait is no part of a run's reported duration, and `turns` is read off the observer, which is the only thing that knows, since a round trip happens inside the executor. A prompt that never started (broken entry, unbindable tool) reports the named `NO_TURNS`. Completion is `isError` unset and the value in both the text block and `structuredContent`; failure (a broken entry, an unbindable tool, or the run itself) is `isError: true` with `status: "failed"` and the same record. `progress` - `McpObserver` is the join between an `Observer` whose `on_event` is synchronous and a peer that must be awaited: `on_event` turns an event into a frame and `try_send`s it into a bounded channel of 64, and `ProgressPump` awaits `notify_progress` on its own task. Nothing on the run's path blocks and the only shared state is three atomics, so no guard exists to hold across an await. A full queue drops the frame and counts it (`dropped()`), because a slow reader must cost itself frames rather than cost the run its latency. Frames: `RunStarted` sends frame 0 captioned with the prompt's name, `SectionStarted` sends the latched `completed` captioned with the section, and everything else is logged only - `SectionFinished` would repeat the frame already sent, `ModelTurn` and `ToolCalled` are traffic. `total` is never sent (an early return means the denominator is unknown) and `progress` is latched with a maximum, so it never decreases. `McpObserver::silent()` is the no-`progressToken` path: no channel, no pump, identical result. `call_tool` reads `context.meta.get_progress_token()` and picks between `dispatch` and `dispatch_with_progress(request, peer, token)`, the two public entry points. `registry` - `RunRegistry::new(&ServerConfig)` is the in-memory record of every run this process started, plus the two limits that gate one. `admit()` waits up to `admission_timeout` for one of `max_concurrent_runs` permits and answers `Some(RunSlot)` or `None`; a refusal is a result naming the wait, not a queue, because every waiting call holds a client connection and a line long enough to outlast the reply deadline becomes a crowd of background runs nobody sized for. `settle(run_id, prompt, version, JoinHandle<RunResult>)` is the deadline race: inside `reply_deadline` the task's own result comes back, past it the handle passes to a supervisor task and the caller gets a `running` snapshot naming the `run_id`. The supervisor is what guarantees a terminal record: a run that finishes normally recorded itself, and one that panicked or was aborted is recorded there as `failed` with "the run did not finish", so no record can stay `running` for the life of the process - which also matters because eviction only reaches a record that finished. `check(run_id)` answers with the record: the finished `RunResult` verbatim, or a synthesized `running` one carrying how long it has been going and `NO_TURNS`, since a partial tally would read as a total. A finished record is swept `retain_completed` after it finished, on each read and each write rather than by a timer; a running record is never evicted, because its result has nowhere else to land. Records live behind a `std::sync::Mutex` reached only by synchronous methods, so no guard can cross an `.await`; the one async method touches the semaphore alone. `server/runner.rs` wires it: a broken entry or an unbindable tool fails before a slot is taken, then admission, then the run on a task of its own - owning a *clone* of the catalog entry, so a reload cannot change the definition under a run in flight - then the race. The task records its own result, which is what makes a run that finished inside its deadline collectable by id too. Progress belongs to the call that asked for it: the pump is finished on both paths, so a backgrounded run reports into a queue with no reader and every later frame lands on the drop counter. 16 unit tests, the timing ones on Tokio's paused clock and the one prompt that must outlive its deadline made slow by a gateway that answers only when the test says so, so nothing in the suite waits on the real clock. `transport` - the crate now serves. `build_router(server, token)` nests `rmcp`'s `StreamableHttpService` (a `LocalSessionManager`, `legacy_session_mode` on so a progress notification rides the session's own SSE stream, 15s keep-alive so an idle proxy does not close it) at `/mcp`, layers the bearer check over what has been registered so far, and *then* adds `/healthz`: the exemption is where the route sits, not a path string the middleware tests, and the rule for a later route is simply which side of the `.layer` call it goes on. The check is per HTTP request, so a rotated token refuses an established session's next call; a request carrying no `Authorization` header, or one whose scheme is not `Bearer`, is refused before any comparison happens, and `Config::load` refuses a `[server].token` that is empty or whitespace alone (`ConfigError::EmptyToken`), so neither a config typo nor a comparison bug can open the surface by itself; the comparison is length-checked and constant-time (the gateway's, mirrored - a third copy would justify lifting it), which hides the position of the first differing byte and not the length; a refusal is 401 with `WWW-Authenticate: Bearer`. `PromptForgeServer` became `Clone` for this: the session factory clones one handler, so every session shares the config, the catalog handle, and the registry - which is what lets a run started in one session be collected by `check_run` from another. `serve_http` binds and serves; `serve_stdio` binds nothing, constructs no auth layer and so reads no token, and logs `[server].bind` as ignored rather than obeying or refusing it. `ServeError` (thiserror, non_exhaustive: `Bind`, `Http`, `Stdio(String)` - rendered, so `rmcp`'s init error does not leak). `main.rs` is `serve [--stdio] <prompts.toml>`, shaped like the gateway's: runtime built in `main`, catalog resolved with `OnBroken::Reject` before anything binds, every fault printed before a nonzero exit. Tracing goes to stdout on HTTP and to stderr on stdio, where stdout is the protocol wire. A boot failure prints its whole cause chain, one indented line per link, since `Display` on a boxed error would report `bind 127.0.0.1:9310` with "address already in use" discarded. 8 unit tests (the auth matrix and `/healthz` driven through the assembled router with `tower`'s `oneshot`, plus the rotated-token case, an empty configured token authenticating nobody, and the keep-alive) + 6 over `Invocation::parse` and the cause chain + 2 integration tests that spawn the real binary: one completes `initialize` and `tools/list` over its pipes, the other gives it a catalog with two independent faults and asserts a nonzero exit with both on stderr. `watch` - the catalog stays current while the server runs, and the two halves are separate on purpose. `Watcher::start(source, config, catalog, sessions)` owns the platform events: `notify`'s recommended watcher over the prompts directory recursively and over the configuration's *directory* non-recursively (an editor saving through a temporary replaces the file, so a watch on the file itself would go with it; the directory's other files are filtered out by name), and every event that is not an `Access` and touches either root pushes a token into a bounded queue. A path is judged against both the configured prompts root and its canonicalized form, resolved once at startup: `notify` does not promise which it delivers - the fsevent backend canonicalizes its watch root - so a relative `[paths].prompts` (the default) or one reached through a symlink would otherwise fail every prefix test and leave a server that watches successfully and never reloads. A `notify` error is logged at error level and queues a token too, which re-registers both roots on the next settled window through a `Weak` handle to the platform watcher (weak, so dropping the `Watcher` still unregisters immediately); a re-registration that fails says at error level that live reload has stopped and a restart is needed once the path is back, and the process keeps serving either way. `debounce` drains that queue and calls back once per settled burst - the window restarts on each event, which is what makes one Windows save with its several events one re-resolution rather than five - and it takes the events as a channel rather than reading a filesystem, so the timing is driven directly on a paused clock. The callback is a future and the re-resolution runs under `tokio::task::spawn_blocking`, since reading and parsing every prompt file is blocking work and has no business on a runtime worker. `[server].watch = false` returns `Ok(None)`: no watcher, no task, boot's catalog for the life of the process. An unwatchable path is a `WatchError` (thiserror, non_exhaustive: `Create`, `Watch`, both carrying rendered detail) and refuses the boot, since `watch = false` is the way to serve without one; dropping the `Watcher` aborts the task and unregisters the watches. `Reloader::reload() -> Reload` is everything a settled window does and takes no events: re-read `prompts.toml`, `Catalog::resolve(.., OnBroken::Retain)`, swap the `ArcSwap`, announce. It never returns an error - under a live service the only useful answer to a candidate that will not resolve is to keep serving the previous catalog and log why - so a catalog-level fault (empty result, stale override, duplicate name, unparsable config) is `Reload::refused` with the previous catalog untouched, while a single prompt that fails validation is a broken entry carrying its error and every other prompt keeps serving. `Reload` also reports `published_changed` (any prompt's name, description, exposure, or problem moved - what a client can read about a prompt whether from `tools/list` or from `list_prompts`, which is wider than the serialized tool list and is what decision 15's contract names) and `ranking_changed` (`Catalog::hash` moved), the second of which is what step 12 will rebuild the picker on, so a body-only edit costs neither an announcement nor a rebuild. What does not reload is the service's own shape: `[server]`, `[gateway]`, and `[paths].prompts` were read once by the transport, the registry, and the watcher itself, so `ignored_changes` names each one that moved in one log line and the reload puts the boot value back rather than half-applying it. A run in flight holds the `Arc<Catalog>` it loaded and finishes under that definition, which the swap cannot reach. `Sessions` is the other end of the announcement: `PromptForgeServer::new` now takes one, `on_initialized` registers the session's `Peer`, and `ListChanged::list_changed` clones the live peers out from under the lock (so no guard crosses the `await`), prunes any whose transport closed, and notifies them on a detached task - a notification nobody reads is not worth holding the next reload for. `ListChanged` being a trait is what lets every reload rule be tested against a recorder with no client anywhere; both it and `Reloader::reload` document that they need a Tokio runtime, since the announcement goes out on a task. 26 unit tests split by the piece they cover - `watch/tests.rs` holds the window on a paused clock and the filter as a pure function over a synthesized event, `watch/reload/tests.rs` holds the reload rules over `tempfile::TempDir` (including one that calls a prompt through `dispatch` before and after a save, so "the second call uses the new body" and "a prompt broken by a save answers with its error rather than the last good copy" are asserted through the handler and not off the catalog's flags), and `watch/fixture.rs` holds the temporary directory both need + 1 integration test, the only thing in the suite that waits on the real clock: it writes a prompt, waits for the platform's own event with a bounded 20ms poll, and asserts both that the prompt joined the catalog and that a live in-process client received `notifications/tools/list_changed`. Next: `need_prompt` - the picker's rebuild path is in (step 11); the retrieval tool behind it is step 12 (descriptors, the picker built at boot with the floor at zero and `top_k` three, `shortlist` on the handler, and `Reload::ranking_changed` driving `ToolPicker::rebuild`).
- `promptforge-gateway` - axum service: `gateway.toml` (Secret + ${VAR} interpolation), model routing, one OpenAI passthrough upstream, bearer auth, POST /v1/chat/completions, GET /health. Config + routing unit tests + 4 end-to-end tests (fake backend + real client).

Lua + args + substitution. A section's Lua block runs in a sandbox with `args`
(raw input) and `sys` (runtime metadata) exposed and a writable `var` table. A
chunk that returns a plain value finishes the run (no model call); otherwise the
prose is `{{ }}`-substituted and sent to the gateway.

- `promptforge-core::lua::run_chunk` - sandboxed VM (string/table/math + base; no io/os/require/load/debug), instruction hook; exposes `args` + `sys`, returns the top-level value and the `var` table (as JSON). 7 unit tests.
- `promptforge-core::subst::substitute` - resolves `{{ args }}` / `{{ var.x }}` / `{{ sys.x }}` (scalar->string, table->JSON, missing->error, single pass, no formulas). 7 unit tests.

An env-built client is still built lazily, on the first section that needs one. ## How to run

Two processes. The gateway holds the credentials; the client points at it.

```
export ANTHROPIC_API_KEY=sk-ant-...      # the vendor key, only the gateway sees it
export PROMPTFORGE_TOKEN=dev-secret      # shared bearer, both processes
cargo run -p promptforge-gateway -- serve gateway.toml &

export PROMPTFORGE_BASE_URL=http://127.0.0.1:8081/v1
cargo run -p promptforge-cli -- run prompts/hello.md
```

## Decisions settled

- Rust multi-crate workspace: promptforge-core (lib), promptforge-cli (bin)
- Edition 2024, resolver 3, rust-version 1.89 (floor set by transitive deps of candle and hf-hub)
- Lint policy in [workspace.lints]: unsafe_code forbid, missing_docs, clippy all=deny + pedantic=warn, unwrap_used deny (doc_markdown allowed for product names); tests allowed unwrap/expect via clippy.toml
- Public error types are #[non_exhaustive] and do not leak dependency error types; tool-picker's `Error` keeps matchable variants and a `detail` string rather than an opaque `Repr` with `#[source]`, because two of its five variants (`ThresholdOutOfRange`, `EmptyShortlist`) carry no cause and are the documented contract of `Config::validate`
- Integration tests are one binary per crate at `tests/it/main.rs`, with an area per module
- Gateway is the only process with an edge to a backend; it holds vendor keys
- Executor targets the gateway: PROMPTFORGE_BASE_URL (default local gateway) + PROMPTFORGE_TOKEN (required)
- Wire structs are NOT shared between core and gateway (JSON is the contract; each side owns its view)
- Gateway v0 supports only protocol = "openai"; Anthropic shim deferred
- Default model claude-sonnet-4-6; override with PROMPTFORGE_MODEL
- Entry point is the first H2, not a named section
- Recursive heading nesting (H2-H6); skipped levels tolerated
- Section ends when the model returns text with no tool calls (auto termination)
- tool_choice: auto when tools present, required when only call is present, omitted when no tools
- `call` is the unified control-flow tool (type discriminator: return, goto, task, fanout) - keeps control-flow tool count at 1
- Lua via mlua (lua54, vendored); sandbox = string/table/math + safe base, no io/os/require/load/debug, instruction-budget hook
- args is a single raw string (caller input); derived values are deduced+stored by the pipeline, not passed
- Exit rule so far: a Lua `return` value ends the run (the return fence); otherwise the section's prose (if any) takes one round trip and control falls through to the next top-level section (fresh context); off the end -> `default_return`, else last reply, else generic
- Substitution namespaces: args (raw string), var (Lua-written), sys (runtime); pure path lookup, no formulas (compute in Lua)
- sys names provenance not immutability: sys.when fixed, sys.now snapshot, sys.id per-context
- Streaming later (Talktron needs it)
